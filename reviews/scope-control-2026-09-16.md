## 3. control でも別のフックが止めていた（事前に想定していなかった）

control の試行 5 件のうち **2 件は「まだ渡されていない先のパスへの先回り」**で、
**3 パス上限のフックに止められて成立しなかった**
（`run.LXDmHeW7` と `run.iCO5dNDn` の 1 起動目が beta.py へ）。
`run.EkQdWOTY` では存在しない `__init__.py` と `main.py` への Read も
同じフックに止められている。

**つまり control は「無防備な腕」ではない。**
スコープ拒否が**単独で効く余地があるのは再読の部分集合だけ**である。

その部分集合で数えると **control 3/3、treatment 0/3、p = 0.100。**
向きは完全に一貫しているが、**N が 3 対 3 では 0.05 に届かない。**

## 4. 腕が交互でないこと（事前登録どおり再掲）

treatment が先に 12 run、control が後から 18 run である。
CLI は両腕 2.1.272 で一致し、機械・枠・プロンプト・土台コミットも同じだが、
**時間差によるモデル側の変化があっても、こちらには分離できない。**
この比較はその分だけ弱い。

## 5. 合否（事前登録された比較ではない）

control pass 6/18、treatment pass 2/12。
**この差を拒否の効果として読んではいけない。**
judge は範囲外 Read を「試みた」時点で `child_extra_read` を落とすので、
拒否されて読めていなくても fail になる（`scope-oneArm` §5）。
さらに両腕とも失敗の多くは `batch_evidence` で、スコープとは無関係である。

## 6. 何が言えるか

言える:
- **拒否のあるビルドでは、範囲外の読みが 4 件試みられて 0 件しか通らなかった。
  拒否の無いビルドでは 5 件中 3 件が通った。**
- **手を伸ばす頻度は両腕で変わらない**（0.29 対 0.25）。
  止まっているのは「読み切り」であって「試み」ではない。
- **偽拒否は両腕で 0。** treatment 側は合計 26 起動ぶんで 1 件も無い。

言えない:
- **「拒否が再読を止める」と統計的に言えない。** p = 0.167（主要）、
  再読部分集合でも p = 0.100。**事前登録の基準に届いていない。**
- 一般化。言えるのはこの枠・この N・この時点についてだけである。

## 7. あと何を買えば答えが出るか

再読の試みは **1 run あたり約 0.17 件**（両腕合わせて 6 件 / 30 run）。
5 対 5（control 5/5、treatment 0/5）なら p = 0.008 になるが、
そのためには**両腕とも 30 run 前後**が要り、$0.26/run で **追加 $16 前後**。

支出は現在 **$9.86**（$5.13 + $4.73）で、上げた上限 $12 の内側だが、
**$16 の追加は $12 では買えない。** 次に進むなら上限を $26 前後にする判断が要る。

**この記録は「向きは一貫、有意ではない、追加 $16 で決着」という状態で閉じる。**
