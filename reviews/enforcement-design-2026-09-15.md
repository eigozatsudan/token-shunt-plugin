# 未遵守3件をどこで強制するか（2026-09-15、設計調査のみ）

`reviews/behaviour-measurement-2026-09-15.md` で、文言追加では
4件中3件の行動が変わらないことが実測された。本記録は**強制点の調査**
であり、実装も課金測定も行っていない。

## 0. 前提の確認：フックは Grep を止められるか → **止められる**

現行 `plugin/hooks/hooks.json` の `PreToolUse` は `Read` / `Bash` /
`Agent|Task` のみで、Grep は対象外である。これは**設定上の限界であって
CLI の制約ではない**。CLI 2.1.271 のマッチャ仕様は

> The matcher is a string: a tool name ("Bash"), pipe-separated list
> ("Edit|Write"), or empty to match all.

であり、ツール名はそのまま書ける。`"matcher": "Grep"` は有効で、
`PreToolUse` は `tool_input` を受け取り `permissionDecision: "deny"` を
返せる。これまで「Grep は hook 対象外」と記録してきたのは
`hooks.json` の内容についての事実であり、不可能性の判断ではなかった。

利用可能なイベントは `PreToolUse` / `PostToolUse` / `Stop` /
`SubagentStop` / `UserPromptSubmit` / `PreCompact` を確認した。

## 1. Grep の2件（検索前メタデータ確認・`head_limit`）

2件は**同じ1つのフック**で扱える。どちらも「Grep 実行の直前に、
入力とセッション状態だけで判定できる」からである。

### 1.1 それぞれ何を見れば判定できるか

| 規則 | 判定に必要なもの | Grep 実行前に揃うか |
|---|---|---|
| `head_limit` の形式（§26.5） | `tool_input` の `output_mode` / `head_limit` / `-A`/`-B`/`-C`、対象ファイルのサイズ | **揃う**。`evals/compare/flow_checks.py` の `position_grep_errors` と同じ判定をそのまま前倒しできる |
| 検索前メタデータ確認（§26.5） | 「この対象について `stat`/`wc -c` が先に走ったか」というセッション状態 | **状態が要る**。単発の `tool_input` だけでは判定できない |

### 1.2 対象ファイルの特定（最大の設計課題）

`head_limit` 判定はサイズ比較を伴うので、対象が**1つのファイルに
確定する**必要がある。Grep の `path` は次のいずれも取りうる。

| `path` の形 | 対象の確定 | 扱い案 |
|---|---|---|
| 単一ファイル | 確定する | 判定する |
| ディレクトリ | 確定しない | 判定しない（対象外） |
| 省略（cwd 既定） | 確定しない | 判定しない（対象外） |
| `glob` 併用 | 展開すればファイル集合 | 展開コストが読めない。初版では判定しない |

**実測での分布**：今回の45実行の親 Grep は20件、**全20件が
`output_mode=content` かつ単一ファイルパス**だった。少なくとも
本スイートの経路では「対象が確定しない」ケースは出ていない。
ただしこれはスイートの性質であって、一般の利用でそうだという根拠には
ならない。ディレクトリ検索を一律に素通しする設計は、
**§26.5 の抜け道をそのまま残す**ことを意味する。

### 1.3 既知レンジ・編集例外の扱い

§26.5 は予算超過ファイルに対し、content search を
**「位置特定」または「既知レンジの確認」に限って**許し、形式を課す。
フックは意図を観測できないので、次の切り分けになる。

| 例外 | フックで判定できるか | 理由 |
|---|---|---|
| 予算内ファイル（§11.6 の編集経路） | **できる** | サイズ比較だけで済む。`position_grep_errors` と同じく予算超過のみ対象にすればよい |
| 「位置特定のため」か「答えを取るため」か | **できない** | 意図は `tool_input` に現れない |
| 既知レンジの確認 | **できない** | 同上 |

したがってフックは**意図を問わず形式だけを課す**設計になる。
これは §26.5 が既に手段基準（`files_with_matches` または
`head_limit` 1-20、`-A`/`-B`/`-C` 禁止）で書かれているので整合する。
意図を問わない分、**正当な位置特定も形式を外れていれば拒否される**。
これは規則どおりの挙動だが、`head_limit` を付けるだけで通るため
回復は1往復で済む。

### 1.4 メタデータ確認には状態が要る

既存の `check-reader-contract` は
`$TMPDIR/token-shunt-reader-<uid>/` 配下に
`(session_id, agent_id)` 単位の状態を持つ。同じ仕組みが使える。

```
check-bash-read (PreToolUse: Bash)  ->  stat / wc -c を観測したら状態に記録
check-grep-form (PreToolUse: Grep)  ->  状態を読み、対象が未計測なら deny
```

`check-bash-read` は既に Bash の `PreToolUse` にいるので、
新規フックは1つで済む。ただし次の限界がある。

- 親が `Read` のメタデータ（hook の deny 文に載るサイズ）で判断した
  場合、`stat`/`wc -c` は走らない。**計測の有無とルート判断の有無は
  同じではない。** 状態には Read deny 由来のサイズ既知も記録する必要が
  ある。
- セッション再開・compact をまたぐと状態が失われる。既存の
  `recover_pending` と同種の劣化設計が要る。

### 1.5 追加往復の費用

deny は親に1往復を追加させる（deny 文を読み、呼び出しを直して再発行）。
今回の実測から見積もる。

| 実測値 | 値 |
|---|---|
| 親ターン総数 / 45実行 | 360（平均 8.0 ターン/実行） |
| 総費用 | $4.68 |
| **親ターン1回あたり** | **約 $0.013** |
| 判定対象になる親 Grep | 20 / 45実行（0.44 件/実行） |

**訂正（`reviews/enforcement-spec-2026-09-15.md` §5）**: この +$0.006 は
「各 Grep で拒否が最大1回」という仮定の概算であり、**最悪値ではない**。
未計測→形式→形式と再拒否が重なり得る。
実行あたりのターン数は 8.0 → 8.4 程度になる。
親が形式を学習して2回目以降は素通りするなら、これより小さい。

比較として、`head_limit` を付けずに 80032 B のファイルを content 検索
した場合、返る本文量は青天井である（`compare-edit-dense-lines` の
3周はいずれもこの形だった）。**1往復 $0.013 は、抑止できる本文取り込み
より安い可能性が高いが、今回は測っていない。**

### 1.6 未解決の設計判断

- ディレクトリ・`glob` 対象をどう扱うか（素通し＝抜け道、
  展開＝コスト不明）。
- フックを**警告**（`additionalContext`）にするか**拒否**にするか。
  警告なら往復は増えないが、今回の測定は「見えていても従わない」ことを
  示しているので、効果は期待しにくい。
- メタデータ確認の deny を、Read deny 由来のサイズ既知でも満たすと
  みなすか。

## 2. `gold_confirmed` — 出力契約の切り分け

### 2.1 これは評価専用ではない。製品の出力要件である

| 出典 | 記述 |
|---|---|
| `README.md:73` | 親の最終回答にも、各事実の `confirmed:` と絶対パスを同じ項目に保持します。 |
| `docs/2026-09-12-token-shunt-design.md:498` | 親の最終回答もこの根拠ラベルとパスを保持する。 |

したがって「評価要件が過剰なので緩める」という選択肢は、
**製品仕様の変更を伴わない限り取れない**。`gold_confirmed` の失敗は
評価器の厳しさではなく、製品仕様どおりに動いていないことを示している。

### 2.2 親の自由文生成だけに任せない方法

今回の測定に、**同じ形の契約が守られている例**がある。

| 契約 | 成立 |
|---|---|
| `status:` / `stop_reason:` の逐語コピー（`child_status`） | 全ケース 3/3 |
| `confirmed:` 項目の保持（`gold_confirmed`） | `auto-explicit-multifile` 0/9 |

違いは文面にある。前者は SKILL.md 冒頭で
**「verbatim as separate plain lines」＝逐語コピー**と書かれており、
親は生成ではなく転記をすればよい。後者は「保持せよ」であって、
何をどう写すかが指定されていない。

検討に値する案（**いずれも未実装・未検証**）:

| 案 | 内容 | 費用 | 弱点 |
|---|---|---|---|
| A. 逐語コピー化 | 子の `confirmed:` 行を、`status:` と同じく**逐語コピー対象**として文面を揃える | 文言のみ。バイト増は小 | 今回3件で失敗した「文言追加」と同じ手段。ただし**転記が守られている実例がある**点が他の3件と違う |
| B. `Stop` フックで検査 | 親の停止時に最終回答を検査し、`confirmed:` 項目が絶対パスを欠けば `continue: false` で差し戻す | 1往復（約 $0.013）。`stop_hook_active` によるループ上限あり | 最終回答の文面をフックに渡す必要がある。停止経路（clear/resume/compact）でも発火するため誤発火の設計が要る |
| C. 子出力の機械的転記 | 子の `confirmed:` ブロックをファイルに落とし、親に「そのファイルを引用せよ」と指示する | 追加 I/O | 親が引用を省略する余地は残る |

**推奨は A を先に試すこと。** 理由は、同じ「転記」という形で
`child_status` が全ケース成立しているという実測があるためで、
文言追加一般が有効だという主張ではない。A が効かなければ B に移る、
という順序を提案する。ただし A も**文言の追加であり、今回止めた手段
そのもの**なので、採否は判断を仰ぐ。
