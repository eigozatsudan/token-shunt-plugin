# 差し戻しフックを製品へ登録するかの判断（2026-09-15）

対象は `plugin/hooks/hooks.json` への Stop フック登録。
根拠は `sendback-remeasure-2026-09-15.md`（実機12実行）、
`sendback-input-path-2026-09-15.md`（入力経路）、
`sendback-scope-2026-09-15.md`（保存コーパス456件）。

## 結論

**条件付きで可。ただし現時点では登録しない。**
効果と安全側の挙動は確認できているが、**登録に必要な前提が4件未了**である
（§3）。これらは実装作業であり、追加の課金測定を要しない。

## 1. 登録を支持する材料

| 根拠 | 内容 |
|---|---|
| 回復 | 実機12実行中6件で差し戻し、**6件とも再開し全行を回復**。`原因不明` 0件 |
| 副作用 | 判定不能・子側の欠落・保持 ok の実行に block を送ったのは、実機12実行・保存474セッションを通じて**0件** |
| 失敗時 | 入力が壊れてもフック内で例外が出ても成功（`{}`）を返し、ターンを落とさない |
| 速度 | `decide()` は実セッション94件で中央値 3 ms、p90 8 ms |
| 上限 | 1回の差し戻しで回復しており、CLI 既定の8回上限に触れていない |

## 2. 登録に伴って受け入れることになる影響

- フックはプラグインを読み込む**全セッションの毎ターン末**で起動する。
  bulk-reader を使わないセッションでも起動し、セッションファイルを解析する。
- 差し戻しが起きたターンは、再生成分だけモデル呼び出しが増える。
  1回あたりの費用は**まだ分離できていない**（`sendback-remeasure` §2.6）。
- 既存の比較評価は、フック込みのプラグインを測ることになる。
  `gold_confirmed` の合否がスキル文面以外の要因でも動くため、
  **評価の基準線の意味が変わる**。

### 3.2 前提2の実施内容（2026-09-15）

**解析の一本化。** `decide()` は親セッションを3回読んでいた
（`read_jsonl`、`check_inputs` 内の `launches` と `final_answer`、
block 経路の baseline 取得）。`se.read_jsonl` を1回呼び、その行を
`check_inputs(rows=...)`・`final_from_event`・`parent_progress` で使い回す形にした。
`launches` と `check_inputs` は `rows=` を受け取る任意引数を足しただけで、
単体で呼べば従来どおり自分で読む。

| セッション | 変更前 | 変更後 |
|---|---|---|
| 17.0 MB | 603 ms | 234 ms |
| 16.0 MB | 492 ms | 203 ms |
| 8.1 MB | 305 ms | 177 ms |
| 5.9 MB | 89 ms | 30 ms |
| 5.7 MB | 216 ms | 149 ms |
| 5.0 MB | 129 ms | 43 ms |

（同一機・`decide()` 3回の中央値。8.1 MB と 5.7 MB の縮み方が小さいのは、
その2件では**子の transcript 読み込み**が支配的で、そこは元から1回だからである。）

**上限。** `se.read_jsonl(path, max_bytes)` は超過時に解析せず `TooLarge` を投げる。
既定は 64 MB（`TOKEN_SHUNT_SESSION_MAX_BYTES` で変更可、不正値は既定に戻す）。
手元の最大セッションが 17 MB・単独解析で約 0.15 s なので、**観測上限の約4倍**にあたり、
通常の作業を除外するための値ではなく最悪値を抑えるための値である。
超過した親セッションは `too_large` として記録し、**block はしない**。
子の transcript が超過した場合は突き合わせができないため
`unavailable`（＝判定不能）とし、通知側だけで親を責めることはしない。

**検証。** `evals/compare` 全体 341件 OK、`evals/run.sh` は pass 125 / fail 0。
保存済みセッション1521件の再実行は前提1の時と**完全に同一**（block 301／no_block 1220）で、
判定は変えていない。追加した7件のうち単一解析の2件は、
旧経路（2回読み）に戻すと実際に失敗することを確認済み。

### 3.3 前提3の実施内容（2026-09-15）

**下限の決定：2.1.269。** 手元に残っていた 2.1.269 / 2.1.270 / 2.1.271 / 2.1.272 の
4ビルドを直接調べたところ、いずれも Stop のスキーマに
`last_assistant_message:o().optional().describe("Text content of the last assistant
message before stopping. …")` を持ち、`hook_event_name:"Stop"` を組み立てる箇所でも
同じ値を渡していた（識別子の難読化名を除けば 269 と 272 は同形）。
したがって **2.1.269 は「導入版」ではなく、ここで確認できた最古の版**である。
それ以前にいつ入ったかは、手元の材料では分からない。

なお、測定時の CLI は 2.1.271 だったが、再起動後に **2.1.272** へ上がっていた。
フィールドの宣言と組み立ては 272 でも変わっていない。

**下限だけでは足りない点。** `last_assistant_message` は新しいビルドでも optional で、
ターンが tool result で終われば欠ける。欠けたときの transcript 経路は、
**フック起動時点では前ターンの本文しか読めない**（`sendback-trial` の block 0件の原因）。
つまり古い CLI かどうかに関わらず、transcript 由来の回答で block するのは
誤った差し戻しになりうる。そこで：

- block は `final_source == 'last_assistant_message'` のときだけ行う。
- transcript 由来で保持違反を見つけた場合は、**checks を記録したうえで no_block** とし、
  理由に取得元と CLI 版を書く。オフラインの再実行（セッションが完結した後の解析）では
  transcript が正しい取得元なので、そちらは回答を明示的に渡して従来どおり判定する。
- 記録に `cli_version` と `below_version_floor` を毎回残す。CLI 版は Stop 入力には無いが、
  セッションの行が自分を書いたビルドを持っているため、**すでに解析済みの行から追加費用なしで**取れる。

**検証。** 追加5件を含め `evals/compare` 345件 OK、`evals/run.sh` は pass 125 / fail 0。
保存済み1585セッションの再実行（回答を明示的に渡す形）は block 301／no_block 1284 で
前提1・2と同一。同じ実行で版の内訳も取れ、
2.1.270 が1032件・2.1.271 が441件・2.1.269 が87件、
**下限未満は14件**（2.1.263 が7、2.1.241 が4、2.1.252 が3）だった。
下限未満の検出が実データで働くことはこれで確認できている。

## 4. 判断の限界

- 根拠は**12実行・2ケース・1台・単一 CLI ビルド**である。
  回復6/6 は母数つきの観測であって、一般的な回復率ではない。
- 再ブロック上限（既定8）に達したときの挙動は**実機未観測**。
  1回で回復したため到達していない。
- 破棄経路（tool result／MCP end-turn／loop tick で終わったターンの
  ブロック破棄）も、今回は全件再開したため**観測されていない**。
  発生率が不明なままである点は `sendback-scope` §2.2 のとおり。
- 子側の欠落（実機2件）と子出力取得不能（実機2件）は、登録しても直らない。

## 5. 推奨する順序

1. ~~§3 の1と2（移設と解析の一本化）~~ **完了**（§3.1、§3.2）。
2. ~~§3 の3（CLI 下限の決定）~~ **完了**（§3.3）。残るは4（評価の基準線の決定）。
3. その上で登録し、登録後の最初の比較評価を**基準線の取り直し**として扱う。

追加の課金測定は、1〜2の後に必要になれば判断する。現時点では不要である。
