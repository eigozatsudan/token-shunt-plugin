### 3.2 前提2の実施内容（2026-09-15）

**解析の一本化。** `decide()` は親セッションを3回読んでいた
（`read_jsonl`、`check_inputs` 内の `launches` と `final_answer`、
block 経路の baseline 取得）。`se.read_jsonl` を1回呼び、その行を
`check_inputs(rows=...)`・`final_from_event`・`parent_progress` で使い回す形にした。
`launches` と `check_inputs` は `rows=` を受け取る任意引数を足しただけで、
単体で呼べば従来どおり自分で読む。

| セッション | 変更前 | 変更後 |
|---|---|---|
| 17.0 MB | 603 ms | 234 ms |
| 16.0 MB | 492 ms | 203 ms |
| 8.1 MB | 305 ms | 177 ms |
| 5.9 MB | 89 ms | 30 ms |
| 5.7 MB | 216 ms | 149 ms |
| 5.0 MB | 129 ms | 43 ms |

（同一機・`decide()` 3回の中央値。8.1 MB と 5.7 MB の縮み方が小さいのは、
その2件では**子の transcript 読み込み**が支配的で、そこは元から1回だからである。）

**上限。** `se.read_jsonl(path, max_bytes)` は超過時に解析せず `TooLarge` を投げる。
既定は 64 MB（`TOKEN_SHUNT_SESSION_MAX_BYTES` で変更可、不正値は既定に戻す）。
手元の最大セッションが 17 MB・単独解析で約 0.15 s なので、**観測上限の約4倍**にあたり、
通常の作業を除外するための値ではなく最悪値を抑えるための値である。
超過した親セッションは `too_large` として記録し、**block はしない**。
子の transcript が超過した場合は突き合わせができないため
`unavailable`（＝判定不能）とし、通知側だけで親を責めることはしない。

**検証。** `evals/compare` 全体 341件 OK、`evals/run.sh` は pass 125 / fail 0。
保存済みセッション1521件の再実行は前提1の時と**完全に同一**（block 301／no_block 1220）で、

### 3.4 前提4の実施内容（2026-09-15）

**決定：比較評価の基準線は「差し戻し抜き」で測る。** 製品としては登録後フックが動くが、
`evals/compare` の既定条件はフックを無効にしたまま走らせる。理由は3つある。

1. **対照が壊れる。** `direct` モードは `--plugin-dir` を渡さないので、そもそもフックが載らない。
   フックを既定で有効にすると、`direct` と委譲モードの差が
   「スキル文面の差」と「差し戻しによる修復の差」の合算になる。
2. **回帰が隠れる。** 再測定では gold 1/12 → 8/12 だった（`sendback-remeasure` §2.4）。
   この大きさの修復が常時入ると、保持に関する文面の劣化は合否に出てこない。
   比較評価の役割は、まさにその劣化を捕まえることである。
3. **既存の基準線が使える。** 抜きで測る限り、これまでの数値と閾値はそのまま比較できる。
   取り直しは要らない。

**切り替え方。** `TOKEN_SHUNT_SENDBACK` が `off`／`0`／`false`／`no`（大小・前後空白は無視）の
ときだけ無効。未設定は有効＝製品の挙動である。runner は `TOKEN_SHUNT_*` を**全て消した後に**
自分で設定するので（`TOKEN_SHUNT_EVAL_FIXTURES` と同じ扱い）、呼び出し側の環境が
評価条件を決めてしまうことはない。無効時はセッションを**一切読まない**：
17 MB のセッションで、入口の実行まで含めて 1回 25 ms（有効時は 282 ms）。

**条件を確かめられること。** `CLAUDE_COMMON` に `--include-hook-events` があるため、
フックが起動したかどうかは各実行の transcript に残る。どちらの条件で走ったかは
推定ではなく**実行ごとに確認できる**。

**登録時に必要な差分（同じコミットで入れる）。** 本記録の時点では未適用である。

```jsonc
// plugin/hooks/hooks.json
"Stop": [{ "hooks": [{ "type": "command",
    "command": "${CLAUDE_PLUGIN_ROOT}/hooks/check-final-answer",
    "args": [], "timeout": 10 }] }]
```

```sh
# evals/compare/run.sh, run_claude() 内、TOKEN_SHUNT_* を消した直後
export TOKEN_SHUNT_SENDBACK=${SENDBACK:-off}   # 既定は抜き。on で差し戻し条件
```

**検証。** 追加3件を含め `evals/compare` 348件 OK、`evals/run.sh` は pass 125 / fail 0。
保存済み1585セッションの再実行は block 301／no_block 1284 で、前提1〜3と同一である。

## 4. 判断の限界

- 根拠は**12実行・2ケース・1台・単一 CLI ビルド**である。
  回復6/6 は母数つきの観測であって、一般的な回復率ではない。
- 再ブロック上限（既定8）に達したときの挙動は、
  `sendback-unobserved-2026-09-15.md` §1 で専用プローブにより実測した。
  上限は「`stop_hook_active` の下で連続して許される再ブロック数」で、
  到達すると最後の差し戻し要求だけが届いてターンが終わり、
  `-p` の `result` は**空**になる（エラーにはならない）。
  製品フックは `stop_hook_active` で見送るため、この経路には到達しない。
- 破棄経路（tool result／MCP end-turn／loop tick で終わったターンの
  ブロック破棄）も、今回は全件再開したため**観測されていない**。
  発生率が不明なままである点は `sendback-scope` §2.2 のとおり。
- 子側の欠落（実機2件）と子出力取得不能（実機2件）は、登録しても直らない。

## 6. 登録（2026-09-15）

`plugin/hooks/hooks.json` に Stop を1本追加した。matcher は付けない（Stop に matcher はない）。

```json
"Stop": [{ "hooks": [{ "type": "command",
    "command": "${CLAUDE_PLUGIN_ROOT}/hooks/check-final-answer",
    "args": [], "timeout": 10 }] }]
```

登録に伴って必要になった付随変更が3つある。いずれも登録した結果として要るもので、
判定そのものは変えていない。

1. **評価の分離。** `evals/compare/run.sh` の `run_claude()` に
   `export TOKEN_SHUNT_SENDBACK=${SENDBACK:-off}` を1行入れた（§3.4）。
   同ファイルには未コミットの変更が併存しているため、**この1行だけを**索引に載せてある。
2. **フックの出力。** 何も言うことがないときは**何も書かない**ようにした（従来は `{}`）。
   judge の分離検査は、hook 応答の**中身**で token-shunt 由来かを判定する
   （`hook_name` は matcher しか載らない）。空応答なら中身の判定に掛からない。
   block 時の本文は `token-shunt: …` で始めるようにし、
   差し戻し要求が誰の要求かが親にも transcript にも残るようにした。
3. **許可リスト。** `judge.py` の `TS_HOOK_NAMES` に `"Stop"`、`TS_HOOKS` に
   `check-final-answer` を加えた。加えないと、登録済みのフックが
   **外来フック**として全委譲ケースを fail にする。
   代償として、分離契約の残余ギャップ（§15）に Stop が1件増える：
   同じ Stop に登録された外来の**通過**フックは、空応答では区別できない。
   `scripts/build-zip.sh` と `evals/test_build_zip.py` の実行ビット検査対象にも加えた。

**検証。** `evals/compare` 349件 OK、`evals/run.sh` は pass 125 / fail 0
（`claude plugin validate` と zip の実行ビット検査を含む）。
zip 内に `hooks/check-final-answer`（0755）と3モジュール（0644）が入ることを確認した。

**実機確認（同日、追記）。** `sendback-live-verification-2026-09-15.md` に記録した。
CLI 2.1.272・登録経由で 4実行（$0.8084）。差し戻し2回・再開2回・全行回復2回、

再ブロック上限に達したときの終了状態は、**今回も未観測**である。

**子側の追加測定（同日、追記）。** `sendback-worker-repair-2026-09-15.md`。
