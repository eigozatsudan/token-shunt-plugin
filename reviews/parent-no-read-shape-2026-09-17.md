## 2. なぜ形が変わったのか — fixture が縮んでいた

`user.rb` は **22,546 bytes** である。Read hook の閾値は 65,536 なので、
**この case では deny が原理的に出ない。**

archive（2026-09-13/14）では同じ file が **67,180 bytes** で、
`bytes=67180/65536` の deny が出ていた。縮んだのは
`4c2fa1e`（2026-09-14、"Fix sixteen review findings…"）である。

つまり:

- Django と archive で見た漏れは、**deny が出る世界**の話だった。
- 今日の 20 run は、**deny が出ない世界**を測っていた。
  3 つ合計 22,806 bytes は step 1 の 16,384 を超えるので委譲すべきだが、
  それを強制する機構は無く、**条文だけが根拠**になる。

`reviews/parent-no-read-rate-2026-09-17.md` の 21.7% は、
**「deny の出ない case で、条文だけを頼りにしたときの率」**と
読み直す必要がある。率そのものは正しいが、一般化の範囲はそれだけ狭い。

## 3. 今日の条文修正が当たらなかった理由

`66a952f` も `e6f59c1` も「**委譲した path を親が読むな**」という形で
書いてある。しかし 25/31 は**そもそも委譲していない。**
委譲していない親に「委譲した path を読むな」は届かない。

私は 2 度とも、形を見ずに条文を書き直した。2 度とも、
直した先は起きている事象の 6/31 しか覆っていなかった。

これは「委譲0回」として既知の事象でもある
（`reviews/zero-delegation-2026-09-13.md`、当時 6 件を調査）。
そこでも原因は単一ではなく、小仕事規則による親生成と
Grep 経由の正答が主だった。**今回の 25 件も Grep + 部分 Read で
正答している。**

## 4. したがって次に効きそうなもの（未検証）

- **条文の 3 度目の書き直しは、優先度が低い。** 直っても 6/31 の側。
- 効くとすれば **routing を強制する側**である。この case は
  「個々の file は hook を通るが、質問に必要な I/O の合計が
  16,384 を超える」形で、これは v0.1 が
  「Out of scope」と明記して自動委譲していない領域そのものである
  （SKILL.md 末尾）。**仕様どおりの挙動を、eval が違反として数えている**
  可能性がある。
- したがって次の判断は「条文をどう直すか」ではなく、
  **「この case は何を測っているのか」**である。
  - 合計超過を自動委譲の対象にする（v0.1 の範囲を広げる）のか、
  - `auto-explicit-multifile` の期待を仕様に合わせるのか、
  - fixture を deny が出る大きさに戻して、元々測りたかった
    「deny の出る世界」を測り直すのか。

いずれも本記録の範囲外で、**まだ何も決めていない。**
