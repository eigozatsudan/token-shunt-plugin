## 1. 再ブロック上限の終了状態

### 1.1 方法

製品フックは `stop_hook_active` で再ブロックを見送るため、**上限には構造上到達しない**。
そこで `stop_hook_active` を無視して毎回 block する使い捨てプローブを書き、
`--settings` で Stop に登録して `claude -p "Say OK"` を走らせた。
プラグインは読み込んでいない。モデルは費用を抑えるため haiku
（上限は CLI 側の挙動で、モデルには依存しない）。

| 条件 | フック起動 | 差し戻し到達 | 親の応答 | 結果 |
|---|---|---|---|---|
| `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=3` | 4回 | 4回 | 4回 | `success` / `turns=5` / $0.0232 |
| 既定（未設定） | 9回 | 9回 | 9回 | `success` / `turns=10` / $0.0378 |

1回目の起動は `stop_hook_active: false`、2回目以降は**すべて `true`** だった。
上限は「`stop_hook_active` の下で連続して許される再ブロック数」として働き、
既定は **8**（初回の block ＋ 再ブロック8回 ＝ 到達9回）である。

### 1.2 終了状態（要点）

- 上限到達時、**最後の差し戻し要求は親に届く**（`user` の
  `Stop hook feedback:\n<reason>`）が、**それに対する応答は生成されない**。
  そこでターンが終わる。
- `-p` の `result` は `subtype: success`、`stop_reason: end_turn`、`is_error: false`、
  終了コード0。**上限到達はエラーとして報告されない**。
- ただし `result` の本文は**空文字列**だった。ターンの最後が assistant のテキストではなく
  フックの差し戻し要求だからである。直前までの応答は transcript に残っているが、
  `-p` の呼び出し元が受け取る回答は**空になる**。
- これは製品フックの経路では起きない。プローブが `stop_hook_active` を無視したときだけ
  再現するもので、実機の差し戻し8件はいずれも1回で回復している。

### 1.3 原因不明として残すもの

両条件とも、最初の再ブロックの直後に
`{"key":"stop-hook-error","text":"Stop hook error occurred · ctrl+o to see"}` が
1件出た。フックは終了コード0で正常な JSON を返しており、
差し戻し自体はその後も届いている。`stop_hook_active` が真のときに block を返したこと
（文書化された契約に反する動作）との関連は**直接確認していない**ため、
**原因不明**として残す。断定はしない。

## 2. 差し戻し1回あたりの費用

### 2.1 方法

追加実行はしていない。**実機で差し戻しが届いた8セッション**
（`sendback-remeasure` の6件、`sendback-live-verification` の2件）の
セッションファイルに残る `usage` から、
**差し戻し要求が届いた行より後の親 assistant メッセージ**だけを積算した。
単価は `cost-structure-2026-09-14` の復元単価
（sonnet-5: 入力 $3.00 固定・出力 $4.92・cache_read $0.319・cache_write $3.36 /Mtok）。

これは対照との差ではなく、**再生成そのものの直接測定**である。

### 2.3 限界

- **単価は復元値**である（残差最大 $0.016、`sendback-scope` §4 の精度の限界と同じ）。
  中央値 $0.0202 はこの残差と同じ桁であり、**有効数字は1桁程度**と読むべきである。
- n=8・2ケース・1台。分布の形は言えない。
- 「差し戻し要求が届いた行より後」を再生成と定義している。
  親が再開後に別の作業（再委譲など）をすれば、それもここに入る。
  今回の8件では再開後のツール呼び出しは0件だった。
- 費用が回復に見合うかは、母数のある回復率が要る。ここでは出さない。
