## 1. 主要: **判定できなかった**

| 腕 | フェンス run |
|---|---|
| control（`SENDBACK=off`） | **1/24** |
| treatment（`SENDBACK=on`） | **0/24** |

**Fisher 正確検定（両側）p = 1.0000。**

**事前登録 §6 の打ち切り規定に該当する**
（「control のフェンス run が 4 未満なら、事象が足りず treatment を判定できなかったと書く」）。

**したがって本測定は、送り返しが効いた証拠にも、効かなかった証拠にもならない。**
treatment が 0/24 であることに三の法則を当てれば上限 12.5% だが、
**control も 4.2% なので、この上限は何も締め付けていない。**

### 1.1 §2.1 の選択バイアスが、予想どおり効いた

基準率は `redmine-dose` の **3/12 = 25%** から取った。今回の control は **1/24 = 4.2%**。

**この case は違反が出たから選んでいる。** 平均への回帰は事前に書いたとおり起きた。
両者は矛盾しない（Wilson 95%: 3/12 は 8.9–53%、1/24 は 0.7–20%、重なる）が、
**25% を設計の基準に使ったのは楽観的すぎた。**

`SENDBACK=off` のデータを合わせると **4/36 = 11.1%**（Wilson 4.4–25.3%）。
**次に設計するならこちらを使う。** 11% を 0 に落とすことを p<0.05 で言うには
各腕 **50 run 程度**が要る（36→0.056、50→0.021）。**今回の 24 では足りなかった。**

## 2. それでも分かったこと: **機構は 1 件、端から端まで動いた**

treatment の `run.dYCTbv4H` で、鎖が全部見えている:

```
SubagentStop  blocked             code fence in the report: ```; ```
SubagentStop  reblock_suppressed  stop_hook_active
Stop          no_block            retention ok
```

worker の 1 通目にフェンスがあり、**フックが落とし**、
2 通目は**フェンス無し・パス付き・status/stop_reason 付き**で返ってきた:

```
confirmed: <abs>/query.rb — last_method_name: joins_for_order_statement
confirmed: <abs>/query.rb — def_line_number: 1691
status: complete
stop_reason: file_fully_read
```

judge も `child_no_body` を通し、`accuracy_any` も通っている。

**これは n = 1 である。率については何も言わない。**
言えるのは「**この機構は実機で不活性ではない**」という一点だけ。
**設計時に一番疑っていたのは「フックは発火するのか」だったので、そこは解消した。**
