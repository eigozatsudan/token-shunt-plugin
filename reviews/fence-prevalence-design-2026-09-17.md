# フェンス違反がどこで起きるかの測定・事前登録（2026-09-17）

`reviews/fence-sendback-2026-09-17.md` §6 の残件。**走らせる前に本記録をコミットする。**

## 1. なぜ効果ではなく所在を測るのか

前回は送り返しの効果を測ろうとして、**事象が足りず判定できなかった**。
control 1/24。基準率を 1 つの case（`redmine-last-query`）の 3/12 = 25% から取り、
**その case は違反が出たから選んでいた。**

**事象がどこにあるか分からないまま効果は測れない。**
本測定は**効果を測らない。違反がどの case で起きるかを数える。**

## 2. 測る問い

**bulk-reader の 19 case のうち、コードフェンス違反が出るのは何 case か。**

区別したい 2 つの読み:

| 読み | 予測（5 run 中 1 件以上出る case 数 / 19） |
|---|---|
| **違反は問い一般に起きる**（率はどこでも 11% 程度） | **約 8**（1−0.89⁵ = 44.5%、19 × 0.445 = 8.5） |
| **`redmine-last-query` に固有** | **約 1** |

**8 と 1 は n = 5 でも見分けられる。** それが本設計の狙いである。

11% は `SENDBACK=off` の既存データをまとめた **4/36**（`fence-sendback` §1.1）。

## 3. 設計

- **対象 = `expect.delegate.child_no_body` が真で `auto` を持つ 21 case。**
  そのうち **`agent_type` が `token-shunt:bulk-reader` の 19 case が主要**。
  **`token-shunt:code-writer` の 2 case（`compare-code-writer-ok`,
  `compare-code-writer-no-ref`）は別扱い**（§5-2）。
- **各 case 5 run、合計 105 run。結果を見て伸ばさない。**
- **`MODES=auto` のみ。** direct には worker が居らず、この問いに寄与しない。
- **`SENDBACK=off` で統一する。** 測るのは**文言だけで守られる率**であり、
  それが将来の効果測定の control になる数字だからである。
- **case の巡回順で回す**（case1..case21 を 5 周）。
  1 case を連続で回さないので、時間帯の偏りが特定の case に集中しない。

### 3.1 n = 5 で言えないこと（先に書く）

**case ごとの率は推定できない。** 0/5 の Wilson 95% 上限は 43% で、
「この case は安全」とは**言えない。** 本測定が答えるのは
**「違反が出る case がいくつあるか」だけ**である。

## 4. N と枠

累計 **約 $73.4**、総枠 **$100**、**残り約 $26.6**。
**本段階の上限 $22**、見込み **$18.9**。

1 run の見積りは直近 48 run の実測から: 平均 **$0.180**（105 run で $18.9）。
**reserve は平均ではなく実測の最大 $0.2423 を丸めて $0.30**
（メモリ `billable-stop-rule-needs-a-mechanism`）。
**run ごとに `spend.py --cap 22 --reserve 0.30` を通す。**

**全 run が実測の最大値で出た場合は $25.4 になり、枠 $22 に収まらない。**
そのときガードは **90 run 前後で止める。**
**止まったら止まったところまでで報告する**（§6）。
**足りなかった case を後から足すことはしない** — 巡回順で回すので、
どの case も同じだけ欠ける。

### 4.1 予算について先に言っておく

**本測定で残額のほとんどを使う。** 終了後に残るのは **$4〜7** 程度。

**効果測定（各腕 50 run ≒ $19）はもう入らない。**
そちらへ進むには**総枠の見直しが要る。**
**本測定を走らせる判断は、それを承知の上でのものとする。**

## 5. 解析（走らせる前に固定する）

**主要: 5 run 中 1 件以上のフェンス run が出た case の数（分母 19）。**
**併せて case ごとの件数をそのまま表に出す。検定はしない。**

**推定の研究であって検定の研究ではない。** n = 5 の 19 群に
均質性の検定を当てても何も言えないので、**最初から置かない。**

**副次、すべて事前に決めたもの:**

1. **19 case をまとめたフェンス率と Wilson 95% 区間。**
   **これが次の効果測定の power 計算に使う数字である。**
2. **code-writer の 2 case は別行で報告する。**
   **現行のフックは `token-shunt:bulk-reader` しか判定しない**
   （`sendback_stop.WORKER_AGENT`）ので、**ここで違反が出ても送り返しは直さない。**
   出た場合は「フックの適用範囲の外に事象がある」と書く。
3. `redmine-last-query` の 5 run を、既存の 4/36 と**並べて記述する**
   （プールはしない。別ブロック・別日なので）。
4. **`child_no_body` がフェンス以外の理由で落ちた件数**
   （引用漏れ、fixture 本文不読）。**本文の漏れはフェンスだけではない。**
5. `accuracy_any`, `child_status`, `child_msg_cap` を全 run で。
6. **case ごとの実費**（次の設計の見積りに使う）。

**中間解析はしない。**

## 6. 打ち切りと、事象が出なかったときの書き方

- 費用が枠に達したとき（`spend.py` が止める）。
- 計器が定義どおり動いていないと分かったときに限り中止してよく、
  そのときは**何が定義と違ったかを数字で示す**。
- **結果の向きや大きさは、止める理由にならない。**

**105 run で 1 件も出なかったとき:**
**「4/36 = 11% は本ブロックで再現しなかった」と書く。**
過去の 4 件が何に集中していたのかは**本測定では分からない**とはっきり書き、
**仮説を作り直して同じデータで検証しない。**
（105 run で 0 件なら、三の法則で率の上限は **2.9%**。これは書く。）

## 7. 予測を外したときにどう書くか（事前に決める）

- **約 8 case で出た**なら、「**違反は問い一般に起きる**」と書く。
  効果測定は**どの case でも組める**ことになる。
- **1〜2 case でしか出ない**なら、「**事象は特定の case に偏っている**」と書き、
  **偏りの理由は本測定では分からない**と添える。
  次の効果測定は**その case に絞って N を積む**しかない。
- **中間の値**（3〜6 など）なら、**そのまま報告する。**
  **後から境界を引いてどちらかに寄せない。**

## 8. 事前に認めている弱点

- **case ごとには何も言えない**（§3.1）。
- **case 集合は eval のものであって、実際の利用の標本ではない。**
  「製品を使う人が何割の確率で本文を見せられるか」の推定では**ない。**
- `SENDBACK=off` なので、**測っているのは文言だけで守られる率**である。
- 費用も挙動も**今日のモデル価格・今日のモデル**に依る。
- Redmine 以外の fixture は小さく、**問いの形も case ごとに違う。**
  フェンスの出やすさは問いの形に依るかもしれないが、**本測定は分離しない。**

## 11. 修正（2026-09-17、機構確認の後・結果を見る前）

§10.1 の機構確認で **suite A / B の case が `isolation` で fail した**:

```
FAIL compare-bulk-facts/auto: isolation: delegate=[9749] direct=None fixture=65669
FAIL auto-bulk-facts/auto:    isolation: delegate=[4446] direct=None fixture=65669
```

**`isolation` は delegate と direct を比べる検査であり、`MODES=auto` では
原理的に評価できない**（`direct=None`）。suite X の case は `isolation` を
宣言していないので通っていた。**私が case 集合の性質を確認せずに設計した。**

### 11.1 計器そのものは動いている

3 run とも **`child_no_body` は評価されている**（checks に存在する）。
落ちた理由は **`isolation` だけ**で、**本測定の outcome ではない。**

**見たのは checks のキー集合と reason の種別だけで、
フェンスの有無も正答も見ていない。**

### 11.2 直すこと

1. **`isolation` は本測定の読み取りから除外する。**
   片腕では定義上評価できない検査であり、**fence とは無関係。**
   verdict の pass/fail は**もともと本測定の outcome ではない**
   （§5 の主要は reasons の中の
   `child_no_body: code fence in child message` の有無）。
2. **正答の列は `accuracy_any` 固定をやめる。**
   実際には case によって **`accuracy_any` / `accuracy` / どちらも無い**の
   3 通りがある（`reader-followup-scope` はどちらも持たない）。
   **`accuracy_any` があればそれ、無ければ `accuracy`、どちらも無ければ空欄**とする。
   **空欄と 0 は違う事実である**（`pairs.py` と同じ規則）。
   以前 `accuracy` を `accuracy_any` と取り違えて 0/20 と誤報した前例がある。

### 11.3 直さないこと

- **走らせ方は変えない。** run の中身は同じで、変えたのは**読み方**だけ。
- **N も case 集合も枠も変えない。**
- **機構確認の 3 run は N に算入する**（同じ手順で走っており、
  継続の可否を結果で判断していないため）。

### 11.4 費用の見通しが上振れしている

機構確認 3 run で **$0.6847（$0.228/run）**。§4 の計画値 $0.180 より高い。
このまま 105 run なら **$23.9** で、**枠 $22 に収まらない。**
**ガードが 96 run 前後で止める見込み。**
§4・§6 のとおり**止まったところまでで報告し、後から足さない。**

## 12. 逸脱の記録（2026-09-17、走行中）

### 12.1 **中間解析をしてしまった**

走行の待ち時間に採点スクリプトを用意し、**動作確認のためそのまま実行した。**
出力には**主要 outcome が含まれていた**（その時点の 8 run について
「1 件以上フェンスが出た case: 0 / 6」）。

**§5 の「中間解析はしない」に反する。**

**言い訳はしない。** 動作確認なら合成データか、outcome を出さない形で
行うべきだった。**採点器を本物のデータで試すこと自体が中間解析である。**

**何も変えていない:** N（各 case 5 run）、case 集合、枠 $22、
`--cap 22 --reserve 0.30`、解析手順のいずれも、この出力を見て変更していない。
**変更していないことは、見てよかったことを意味しない。**

**以後、ブロック完了まで採点器を実データに当てない。**

### 12.2 reserve を超える run が出た

`compare-one-line` の 1 run が **$0.4806** だった。
**§4 の reserve $0.30 を超えている**（設定時点の実測最大は $0.2423）。

結果として枠 $22 を **最大 $0.18 程度超え得る**。**超えたらそのまま記録する。**

「直近の最も高い 1 run」であって平均ではない）。
