**どの数字も事前に見ると決めていなかった。** 追加の課金はしていない。

## 1. 床はどこから来たか — 委譲の前に親が何をしたか

| 委譲前の親の道具列 | 対照 | 処置 |
|---|---|---|
| `Bash` のみ | **31** | 1 |
| `Bash` → `Skill` → `Read` | **9** | 0 |
| **何もせず即 `Agent`** | 0 | **27** |
| `Skill` → `Read` | 0 | 8 |
| `Skill` → `Read` → `Bash` / `Skill` → `Bash` → `Read` | 0 | 4 |

**対照腕は 40/40 で、委譲の前に Bash を打っている。**
その中身は **`wc` 36 件、`for` ループ 3 件、`stat` 1 件**——
**すべてファイルの大きさを測る命令である。**

**処置腕は 27/40 が、何も見ずにいきなり委譲している。**

**これが床の正体だろう、というのが本探索でいちばん強い観察である。**
対照腕は「まず大きさを測り、大きいので委譲する」。
処置腕は「計画文書の形に従って、測る前に委譲する」。
**道は違うが、行き先が同じだった。**

**ただしこれは相関の記述であって、因果ではない。**
「`wc` を打ったから委譲した」ことを、本探索は示していない。
**それを言うには、大きさを測れない条件を作って比べる必要がある。**

## 2. deny は一度も出ていない、という事実の扱い

結果記録 §5 に書いたとおり、**deny は 80 run で一度も出ていない。**
本探索はその理由を一段だけ細かくする: **親は corpus を読もうとすら
しなかった。** 対照腕は `wc` で大きさを見て、読まずに委譲した。

**したがって本測定は「deny がある世界」を測ってはいない。**
測ったのは「**deny を引くほど大きいと、親が読む前に気づける世界**」である。
**この 2 つを分離する設計は、次に測るなら要る。**

## 3. 親の文脈にはむしろ処置腕のほうが多く入っている

| 指標（中央値） | 対照 | 処置 |
|---|---|---|
| `parent_added_utf8_bytes` | 8,128 | **11,498** |
| `parent_added_tokens_est` | 2,032 | **2,874** |

| `wall_ms` | 8,052 | **15,591** |

**corpus のバイトはどちらも 0 である。** 増えているのは
計画文書の形そのもの（処置腕の prompt は長い）と、そこから出る出力である。

**「文脈保護」を漏れ率だけで見ると両腕引き分けだが、
親に入る総量で見ると処置腕のほうが 1.4 倍多い。**
**これは事前に決めた指標ではない。** 主張ではなく、次の設計への材料として置く。

corpus ではないので `parent_no_read` にも `parent_read_bytes` にも

**機構の説明を読むために親の文脈が使われている run が 4 件に 1 件ある。**

## 5. `ScheduleWakeup`（結果記録 §7、設計 §11.4）

**親がこれを呼んだ run: 対照 14 / 40、処置 23 / 40。**
いずれも worker の完了待ちで、`delaySeconds: 300`、
`reason: "Waiting on bulk-reader worker to finish reading Django source files"`
の形である。

`run.sh` の `--allowedTools` は
`Read,Edit,Grep,Glob,Agent,Task,Write,Bash` であり、**この道具は挙げていない。**
**環境に別経路で入っている。**

**測定への影響は本探索では判定できない。** 少なくとも
`parent_no_read` と `accuracy` の判定には入らない。
ただし **`wall_ms` の最大値（対照 67.5 s、処置 69.2 s）**は
この待ちを含んでいる可能性がある。

**これは eval 環境の設定の問題であって、plugin の欠陥ではない。**
次に走らせる前に、`--allowedTools` の指定が実際に効いているかを
確かめるべきである。
