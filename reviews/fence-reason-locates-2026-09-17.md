# 送り返し文が「どこを消すか」を言うようにした（2026-09-17）

`reviews/fence-sendback-2026-09-17.md` §4 で見つけた瑕疵への対応。**課金なし。**

## 1. 何が起きていたか

送り返し文は**一致したフェンス行をそのまま並べていた**。
素のフェンス（情報文字列なし）だと、開きも閉じも同じ文字列なので:

```
code fence in the report: ```; ```
```

**worker に何も伝わらない。** どの行か、何を貼ってしまったのかが分からない。

実測（`run.dYCTbv4H`）ではこの文言でも worker は直せた。
**一度直せたことは、次も直せる理由にはならない。**

## 2. 直したこと

**マーカー行ごと**ではなく**フェンス塊ごと**に 1 件、
**開き行の行番号**と**中の最初の非空行**を付ける:

```
line 3: ``` — def joins_for_order_statement(order_options)
```

- **行番号**があるので、報告のどこを指しているか一意に決まる。
- **中身の 1 行目**があるので、何を貼ったのかが分かる。
- 情報文字列（` ```ruby `）は残す。
- **中身の引用は 60 文字で打ち切る**（`_QUOTE_MAX`）。
  **塊を特定するには足りるが、本文の引用にはならない長さ。**
  ここは worker 自身の文脈に返すだけで親には行かないが、**長さは絞る。**
- 空のフェンスは `line 1: ``` (empty fence)` と言う。**黙って何も出さない道は塞いだ。**
- **閉じないフェンスも 1 件として報告する**（以降が中身）。

### 2.1 マーカーは種類を問わず開閉が交互

` ``` ` と `~~~` を区別せず、**現れた順に開き・閉じと解釈する。**
報告は Markdown として描画するものではなく、**単純な規則のほうが塊を取りこぼさない。**

## 3. テスト（9 件。**実装より先に書いて RED を確認した**）

塊 1 つは 1 件（従来は開閉で 2 件だった。**契約を変えたので既存テストも直した**）/
**行番号と中身が入る** / 情報文字列が残る / **長い行は打ち切られ `…` が付き、
全体が 200 文字未満** / **空フェンスは "empty" と言う** /
中の最初の**非空**行を採る / **閉じないフェンスも報告** / 2 塊は 2 件 /
フック側で**送り返し文に中身と行番号が出る**。

## 5. これは測定ではない

**文言が実機で worker により通じやすいかは測っていない。**
`reviews/fence-sendback-2026-09-17.md` は事象不足で主要な問いを判定できておらず、
**本変更もその判定を助けない。**
直したのは「読み手に何も伝えない文字列を出していた」という、
**測定を待たずに分かる欠陥のほうである。**
