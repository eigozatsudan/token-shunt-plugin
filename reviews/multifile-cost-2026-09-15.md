## 3. 増分がどこに集中しているか

各区間を `direct` の対応部分と引き算すると、3周とも増分が正確に再構成できる
（子は非ワーカーベースライン $0.0011 を控除）。

| 周 | 親の準備＋委譲 | 委譲先 | 受領後 | 合計 | 実測の差 |
|---|---|---|---|---|---|
| 1 | +0.0396 (54%) | +0.0199 (27%) | +0.0136 (19%) | +0.0731 | +0.0730 |
| 2 | +0.0413 (54%) | +0.0201 (26%) | +0.0148 (19%) | +0.0762 | +0.0763 |
| 3 | +0.0702 (65%) | +0.0234 (22%) | +0.0138 (13%) | +0.1074 | +0.1073 |

**増分の過半（54〜65%）は「親の準備＋委譲」に集中している。**

> **この比率の限定**: `direct` は `result` イベントが1個で区間に分離できない。
> 上の引き算は、`direct` の親費用（$0.0199〜0.0208）を**すべて準備区間から
> 控除する**配賦として計算している。したがって 54〜65% は**配賦上の比率**で
> あって、「対応する処理同士の実測差」ではない。`direct` の親費用のうち
> 最終回答の作文に相当する分がどれだけあるかは未分離であり、その分だけ
> 準備区間の増分は過大に、受領後の増分は過小に出ている可能性がある。
> 順位づけ（準備区間が最大、受領後が最小）は、受領後の絶対額が
> 3周とも $0.0136〜0.0148 と `direct` の親費用の8割弱に達しない点からも
> 支持されるが、比率そのものは配賦依存の値として扱う。
受領後の処理は3周とも +0.0136〜0.0148 とほぼ一定で、最小の区間。
周ごとの総額のばらつき（+0.073 → +0.107）も、ほぼ全部が準備区間の差である
（run-3 の cacheR が 83.5k → 151.4k と約1.8倍）。

準備区間の内訳として実測から言えること:

- **キャッシュ書き込みは委譲モードにのみ発生する**（実測）。`direct` は
  cacheW 0、`auto` は 7825〜10690。
  **何が書き込まれているかは現時点では未特定。** プラグイン（フック・スキル・
  contract）の内容は候補だが、委譲仕様そのもの、Agent のツール結果、
  子の返答なども書き込み対象になり得る。原因の特定には内訳の追跡が要る。
- **親の出力が約3倍**（455〜545 → 1246〜1777）。委譲の呼び出し仕様を
  親が書き出す分である。
- 受領後は cacheR 約31k を読み直している。子の結果を受けてからの
  2回目の文脈ロードにあたる。

## 6. 準備区間の道具列比較（3周、追加実行なし）

`auto` モードの準備区間（1個目の `result` イベントまで）の親の手番。

| 周 | 親の手番 | turns | 親の out | cacheR |
|---|---|---|---|---|
| 1 | Read user.rb → Read notifiable.rb → Read welcome_email_job.rb → Agent | 5 | 1246 | 83518 |
| 2 | Read user.rb → Read notifiable.rb → Read welcome_email_job.rb → Agent | 5 | 1441 | 83670 |
| 3 | **Skill(bulk-reader)** → `wc -c` → **Read hooks/reader-call-contract** → Agent | 6 | 1777 | 151397 |

`welcome_email_job.rb` 131 B。

### 6.1 run-3 で増えた手番

run-3 だけが `Skill` を開き、`hooks/reader-call-contract` を読んでいる。
これが +1 turn と cacheR の 83.5k → 151.4k（約1.8倍）の内訳にあたる。
読み込んだのは SKILL.md 本文（6558 B）と contract（877 B）。

ただし run-3 の**ルーティング自体は正しい**。親は fixture を一切読まず、
3パスすべてを子に渡している。

### 6.2 run-1 / run-2 の重複読み込み（本質的な無駄）

run-1 / run-2 は**親が3ファイルすべてを自分で Read したうえで、
`user.rb` を子にも渡している**。`user.rb` は 22546 B で 16384 の境界を
超えるため、本来は親が読まずに委譲する対象である。結果として

- 22546 B の本文が**親の文脈に入る**（委譲した意味が消える）
- 同じ `user.rb` を**子がもう一度読む**（子の cacheW 12.3k の主因）

という二重の I/O が発生している。これは §2.1.1 で確定した
**16384 規則の到達性欠落と同一の原因**であり、この2周は退行状態の
description で走っている。v2 の修正がこの重複に効くかは、対照実行で
確認できる。

なお run-1 / run-2 が `parent_no_full_read` を通過しているのは、
このチェックが deny 閾値（65536 B）を基準にしているためで、
16384 の運用規則違反は検出していない。

### 6.3 委譲指示に重複している内容

3周すべての Agent prompt に、**同一の応答契約ブロックが逐語で再出力**
されている。

```
One bullet per fact: confirmed: <absolute path> — <symbol>: <fact>.
unconfirmed for missing evidence. No source lines or code fences.
Max 4000 chars. End with two plain lines: status: complete|partial,
then stop_reason: <reason>.
```

229 chars / 231 B。prompt 全体に占める割合は run-1 37%、run-2 39%、
run-3 23%。これは `hooks/reader-call-contract` の 243 B の応答契約ブロックと
同じ内容であり、run-3 では**契約を読んだ直後にその中身を書き写している**。

親が毎回この定型を出力している分は、親の出力トークンとして課金され、
かつ子側の入力にも乗る。

### 6.4 絞り込んだ削減候補

1. **重複読み込みの解消**（最大）。run-1 / run-2 の「親が読んでから委譲」を
   無くす。v2 の description 修正が直接狙っている挙動で、対照実行で
   効果を測れる。
2. **応答契約の再出力をやめる**。定型 229 chars を親に書かせず、
   子側の system prompt（`agents/bulk-reader.md`）に常駐させ、
   親の prompt は質問とパスだけにする。契約の二重管理を無くす副次効果もある。
3. **Skill 本文の読み込み回避**。run-3 は contract だけで委譲できる状況で
   SKILL.md 本文（6558 B）も読み込んでいる。deny 経路では本文を読まずに
   済んでいるので、明示委譲でも contract だけで足りるかを確認する。

### 6.5 対照実行で確かめること

上の3候補は、どれも準備区間のトークンを減らす方向だが、
**削減額は未測定**である。対照実行では `auto-explicit-multifile` を
同一 fixture・同一プロンプトで回し、(a) v2 description、(b) 応答契約を
子側に移した版、(c) 両方、の準備区間トークンと cacheW を比較する。
cacheW に何が書き込まれているかの特定（§3 の未特定事項）も同じ対照で行う。
