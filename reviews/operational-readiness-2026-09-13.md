## 確認済み指摘

### 1. [P2] コメントを構文として解析し、見逃しと誤拒否が起きる

箇所: `plugin/hooks/check-bash-read:155` の `scan_ops`、同 `:199` の `tokenize`。

| 実行コマンド | フック | 実 stdout |
|---|---|---:|
| `cat L` | deny | 82000 bytes |
| `cat L # > discarded` | pass | 82000 bytes |
| `cat S # L` | deny | 1000 bytes |

引用外かつ単語開始位置の `#` がコメント開始として処理されない。
コメント内の `>` が CLEAN_GT を立てて早期通過させ、逆にコメント内の実在パスが
ファイル引数として検査される。通常のコメント付きコマンドで起こり、意図的な回避を
必要としない。ネスト・変数展開・未知コマンドの既知の非対応経路とは異なる。

修正方針: 演算子走査とトークン化の双方で Bash のコメント境界を揃える。
引用内の `#`、`file#name`、エスケープした `\#` はコメント扱いしない。
上記の pass/deny 双方向を回帰ケースに追加する。

### 2. [P2] パイプ後段の cat の明示ファイルが判定から抜ける

箇所: `plugin/hooks/check-bash-read:444`。

`cat S | cat L` と `cat S | head -c 1 | cat L` はいずれも pass、
実 stdout は 82000 bytes。末尾が cat 等なら先頭段だけを検査して終了している。
後段 cat は明示ファイルを読むため、先頭の小ささは出力量の上限にならない。

偽陽性裁定: 未知の末尾コマンドによる既知の fail-open ではない。
ただし「末尾 cat なら先頭に戻る」という現行設計には一致するため、
設計不一致ではなく、設計と実装に共通する運用上の隔離不足として扱う。

修正方針: 既知の非縮約段の入力ファイルも検査し、後段のファイル入力を
先頭段のサイズで代用しない。`tee` の引数は出力先なので cat と同一視しない。

### 3. [P2] stdout に戻すリダイレクトも「本文が出ない」と判断する

箇所: `plugin/hooks/check-bash-read:449`。

`cat L > /dev/stdout` は pass、実 stdout は 82000 bytes。
実行は exit 0。`>` の存在だけで通過し、出力先を検査していない。

偽陽性裁定: 通常ファイルへの出力で親コンテキストが増えないケースとは区別した。
現行設計の無条件リダイレクト通過には沿うが、本文隔離の説明が成立しない例である。
現在の Linux 環境で成立を確認したもので、全 OS への一般化はしない。

修正方針: stdout に戻る既知の出力先は早期通過させず通常判定へ戻す。
特殊ファイルやリンク等も含め保証できる出力先の範囲を明示する。

## 除外した候補と既知の制限

- **インストール先の空白によるフック起動失敗: 偽陽性。** `hooks.json` は `args: []`
  を指定した exec form。shell 経由の試験では失敗するが、その試験は実際の起動方式と
  異なる。空白を含むディレクトリで exec form 相当の直接実行を行い、3 フックとも成功。
  [公式 hooks reference](https://code.claude.com/docs/en/hooks#exec-form-and-shell-form)
  でも args 指定時は shell を介さずパスを単一の実行ファイルとして扱う。
- symlink のサイズ取り違え、leading cd の未追跡、巨大単一行を無制限に読み込む問題は、
  現行実装と回帰テストで対策を確認。過去の欠陥を再掲しない。
- 過去の評価レビューをそのまま採用しない。現行 judge は fixture 非依存の fence / 長文
  チェックを持ち、欠測、検証実行、編集順序、ルーティング等の制御テストも通過した。
  これは全ての不正 transcript を防ぐという保証ではない。
- `cat S | head` の拒否、複合コマンドで targeted head/tail も全文閾値になる挙動は
  現行仕様の保守的な拒否。新規バグとはしないが、日常利用時の摩擦にはなる。
- 未知コマンド、展開、繰り返し targeted Read、遅い FS での timeout、子の最終回答に
  対する強制上限の不在は README の既知の制限。これらを排除する強い隔離保証はできない。
- author 警告と費用削減未証明は、コード不具合には数えない。
