### 2.1 `auto-routing-boundary-16k-plus/auto`（3/3 vs 変更前 1/3）— **本プラン起因の退行**

> **訂正。** 本稿の初版はこれを「本プラン起因ではない」と結論していた。
> 根拠は deny が0件であることだけだった。deny 0件で除外できるのは
> deny 判定とテンプレート描画までであり、**変更箇所と実行経路の照合を
> していなかった**。照合した結果、結論は逆になる。

失敗チェックは `agent_type` / `agent_calls` / `child_reads_once` /
`parent_no_full_read`。理由は
`no Agent with subagent_type=token-shunt:bulk-reader (saw [])` で、
親が委譲せず自分で読んでいる。

#### 変更箇所と実行経路の照合

本プランが変更した成果物のうち、**deny が発火しなくても実行経路に乗るもの**が
2つある。

| 変更した成果物 | deny=0 で経路に乗るか |
|---|---|
| `check-file-size` / `check-bash-read` の deny 描画部 | 乗らない |
| `reader-call-contract`（新規） | 乗らない（deny 時のみ読まれる） |
| `skills/bulk-reader/SKILL.md` 本文 | `Skill` 呼び出し時のみ |
| **`skills/bulk-reader/SKILL.md` frontmatter の `description`** | **常に親の文脈にある** |
| **`agents/bulk-reader.md` の `description`** | **常に親の文脈にある** |
| `agents/bulk-reader.md` 本文 | 子の system prompt（`Agent` 呼び出し時） |

#### 原因

このケースは **16384バイトという総I/O境界**のテストであり、
フックの deny 閾値（`MIN_BYTES=65536` / `MIN_LINES=350`）には遠く届かない。
`b16385.txt` は 16385 バイトなので、**deny は原理的に発火しない**。
この境界で親を委譲させられる唯一の仕組みは、常に親の文脈にある
スキルの `description` である。そこが Task 6（`9106001`）で書き換わり、
**16384 バイトのルーティング規則が description から消えている**。

> **診断の訂正（2026-09-15）**: 当初これを「規則の削除」と書いたが、正確では
> ない。16384 規則も Grep のルート決定規則も SKILL.md の**本文には残っている**
> （`plugin/skills/bulk-reader/SKILL.md` の 1. と「Route before searching」）。
> 欠陥は**到達性**にある。本文が読まれるのは親が Skill を開くと決めた後であり、
> 「いつ開くか」を決めるのは常に文脈にある description だけである。deny が
> 発火しない条件でしか適用されない規則は、description に名前が出ていなければ
> 到達されない。したがって症状は同じでも、修正対象は本文ではなく description。

変更前（`1ad21b0`）:

> Use before content search when metadata shows a needed whole file exceeds
> 350 lines or 65536 bytes (default hook thresholds), **total needed I/O
> exceeds 16384 bytes**, or a Read/Bash hook denies it. …
> **Keep known ranges totaling at most 16384 bytes in the parent only if
> each Read passes the hook**; file count alone is not a trigger.

現在（`HEAD`）:

> Not needed when the deny already carries the call spec — follow the deny
> and delegate. Use for explicit delegation with no hook deny, batch
> boundaries (4+ paths, cross-file relationships), ambiguity between
> confirmed/unconfirmed evidence, and retry or escalation decisions after a
> partial. …

現在の description にはバイト閾値が一切無い。

#### 裏付け

同じ境界を挟む3ケースの挙動が一貫している。

| ケース | サイズ | 期待 | 今回 |
|---|---|---|---|
| `auto-routing-boundary-16k-minus` | 16383 B | 親が自分で読む（`agent_zero`） | 通る |
| `auto-routing-boundary-16k-equal` | 16384 B | 親が自分で読む（`agent_zero`） | 通る |
| `auto-routing-boundary-16k-plus` | 16385 B | **委譲**（`bulk-reader`） | **3/3 失敗** |

規則を失った親が一律「自分で読む」側に倒れた場合に期待される分布と
完全に一致する。「委譲しなくてよい」2ケースは通り、「委譲すべき」1ケースだけが
落ちる。変更前は 2/3 通っていた。

#### 位置づけ

**Task 6 の SKILL.md 削減が、deny テンプレートでは運べないルーティング規則を
落とした。** deny が発火しない境界の話なので、テンプレートに載せることは
そもそもできない。最終レビューが「SKILL.md の削減で、deny テンプレートが
運べないものを落としていないか」を問うており、その答えが**落としていた**という
ことになる。

修正候補は `description` への 16384 規則の復帰。description は常に親の文脈に
あるメタデータなので、復帰させても `Skill` 読み込みは発生せず、本プランの
往復削減とは競合しない。ただし description の変更はルーティング挙動そのものを
変えるため、`auto-routing-boundary-16k-{minus,equal,plus}` の3ケースで
再測定が要る。

### 2.1.1 修正と再測定（v1 / v2、各3周）

対象6ケース（境界3 + content search 3）を `bash run.sh <ids>` で3周ずつ、
description の2案について実行した。判定は `last-run.json` の合否に加え、
**トランスクリプトから実際の道具順序**を取った（静的な文言 assert は
到達性の担保であって、行動の証拠ではない）。

- **v1**: 閾値だけを description に戻した案。
- **v2**: 「最初の Read より前に `stat`/`wc -c` でサイズを測る」を
  **委譲条件より先に**置き、ファイル全体サイズと必要 I/O を分離し、
  既知レンジ合計 ≤16384B の親保持を維持した案。

#### 境界3ケース（mode=auto、3周中の回数）

| ケース | サイズ | 期待 | v1 meta1st | v1 route_ok | v2 meta1st | v2 route_ok |
|---|---|---|---|---|---|---|
| `…-16k-minus` | 16383 B | 親 | 1/3 | 3/3 | **3/3** | 3/3 |
| `…-16k-equal` | 16384 B | 親 | 1/3 | 3/3 | **3/3** | 3/3 |
| `…-16k-plus` | 16385 B | 委譲 | 0/3 | **0/3** | **3/3** | **3/3** |

**meta1st と route_ok の同時成立**は v1 で 2/9（`minus`・`equal` 各1周）、
v2 で **9/9**。

v1 で `minus`/`equal` の route_ok が 3/3 なのは、routing が正しかったからでは
ない。測らずに直接読んでも「親が読む」に落ちるため期待と一致しただけで、
同じ周の meta1st は 1/3 である。**成否だけでは手順の有無を判定できない。**

v2 の `16k-plus` で**3周に共通する**のは、最初の手番がサイズ計測で、
その後に委譲していることだけである。

```
Bash stat -c '%s' | wc -c <path>   →  …  →  Agent token-shunt:bulk-reader
```

3周のうち2周（run-1 / run-3）はその間に `Skill` を開き、
`hooks/reader-call-contract` を読んでから Agent を呼んでいる。
残る1周（run-2）は `Skill` を開かず、description だけで直接委譲した
（結果として worker-model の解決を誤っている。下記「残る失敗」を参照）。
共通しているのは「測ってから委譲する」順序であって、Skill を開くかどうかは
周によって異なる。

v1 は3周とも `Read(b16385.txt)` のみで、サイズを測る手番が存在しなかった。

#### 境界以下の親保持（whole-file ケースのみ）

v2 で `minus`/`equal` が委譲した周は **0/3**（v1 も 0/3）。
メタデータ確認を先に義務づけても、境界以下での不要な委譲は増えていない。

ただしこの2ケースはいずれも**ファイル全体が 16384B 以下**の whole-file
ケースである。**大きなファイルの一部だけを読む「既知レンジ合計 ≤16384B を
親に留める」規則は、今回の6ケースには含まれておらず未確認。**

> 補足（2026-09-15）: この経路を検証するケースはスイートに既に存在する
> （`auto-known-range`: 25953 B のファイルで lines 200-210 をプロンプトが
> 明示、`agent_zero` と範囲指定 Read を期待）。再測定の6ケースに
> 入れていなかっただけである。`reviews/grep-route-fix-verify-2026-09-15.md`
> で3周とも親保持を確認した。

#### content search

両 grep ケースの fixture は 5613 B / 5674 B、spec の期待は `agent_zero`
（＝親が処理する）。したがって**親保持が正解**であり、委譲しないことは
欠陥ではない。

| ケース | 期待ルート | v1 route_ok | v2 route_ok | Grep 前の判断（v1 / v2） |
|---|---|---|---|---|
| `auto-edit-grep-location` | 親 | 9/9 | 9/9 | なし / なし |
| `auto-edit-grep-ambiguous` | 親 | 9/9 | 9/9 | なし / なし |
| `compare-edit-dense-lines` | 委譲 | 3/3 | 3/3 | **あり / あり** |

ルート判断が実際に問われるのは、閾値を超える `compare-edit-dense-lines`
（80034 B）だけで、そこは **v1・v2 とも3周正しい**。順序も契約どおり:

```
Bash wc -c  →  Read reader-call-contract  →  Agent bulk-reader
            →  Grep '^EDIT_MARK=' -n（委譲の後、位置特定のみ）
            →  Read(offset, limit)  →  Edit
```

5.6 KB の2ケースは、測っても測らなくても親に落ちるため、Grep 前の
メタデータ確認は v1・v2 とも発生しない。**この2ケースは
「Grep 前のルート決定」の検出力を持たない**、というのが再測定の結論。
`content search の前にルートを決める` 規則の退行は、今回の測定範囲では
確認されなかった。

#### 合否と残る失敗

v1 の失敗数 2 / 2 / 5、v2 は 1 / 3 / 1。いずれもスイート既知の非決定性の
範囲で、失敗数そのものは判定に使わない。ただし失敗の**内訳**は変わった。

- v1 の `16k-plus` は3周とも `agent_type, agent_calls, parent_no_full_read`
  ＝**そもそも委譲していない**。
- v2 の `16k-plus` は 1周のみ失敗し、内訳は
  `child_reads_once, child_status, requested_model, resolved_model,
  retry_policy` ＝**委譲はした上で worker-model の解決を誤った**。
  その周だけ親が `Skill` を開かず description だけで委譲しており、
  リテラル `auto` が Agent に渡っている（本文の「the literal string `auto`
  never reaches Agent」が親に届いていない）。ルーティングとは別系統の欠陥で、
  **description だけで委譲する経路の worker-model 解決**として切り出す。

#### 結論

- **v1 は確定的に不十分**。閾値を description に戻すだけでは `16k-plus`
  の退行は解消しない（route_ok 0/3）。
- 「手順の欠落が原因」という仮説は **v2 で支持された**。メタデータ確認を
  委譲条件より先に明示すると、境界3ケースで meta1st と route_ok が
  1/9 → 9/9 に揃い、境界以下の過剰委譲も増えない。
- ただし3周では安定と断定できない。2/9 → 9/9 の差と道具順序の変化は
  仮説を支持するが、スイートのばらつきだけでは説明できない、とまでは
  この測定範囲では言えない。

### 2.2 `auto-large-writer/haiku`（3/3 vs 変更前 0/3）

3周それぞれ**異なる理由**で失敗している。単一の再現する欠陥ではない。

| 周 | 失敗チェック | 理由 |
|---|---|---|
| run-1 | `agent_type`, `agent_calls`, `no_parent_write`, `writer_body_absent` | 委譲せず親が Write |
| run-2 | `parent_bash` | 検証コマンド未実行 |
| run-3 | `child_format` | 子の返却形式（パス・行数・3〜5箇条）不備 |

**本プラン起因を示す証拠は無い。** 3周とも親の道具列は
`Read(greeter.py) → Skill(code-writer) → Agent(code-writer) → Bash(unittest)`
（run-1 のみ `Read → Write → Bash`）で、**deny は0件**。
2.1 と同じ照合を行うと、deny=0 でも経路に乗る変更は
`bulk-reader` の2つの `description` だが、このケースが選択・実行しているのは
`code-writer` のスキルとエージェントであり、本プランはどちらにも触れていない。
`bulk-reader` の description が親の文脈に存在すること自体は変わらないため
影響が厳密に0だとは言えないが、それを支持する挙動は観測されていない
（委譲先の誤選択や `bulk-reader` の呼び出しは3周とも発生していない）。
3周が毎回別の理由で落ちていることと合わせ、現時点では
**このケース/モードが現在の作業ツリーで不安定である**という以上の主張はしない。

  往復削減を deny 以外の経路にどう届かせるか（あるいは届かせないと決めるか）が
  次の設計判断になる。
- **`4+ paths` と「file count alone is not a trigger」の整合性（設計確認事項）**。
  description は `batch boundaries (4+ paths, ...)` を委譲条件として挙げる一方、
  本文の 1. は「File count alone is not a trigger」と書く。本文の 2. は
  「1回の呼び出しは最大3パス、4+ は3件ずつに分割」というバッチ規則であって
  委譲の発火条件ではないので、両者は本来矛盾しない。ただし description だけを
  読む親には「4+ パスなら委譲」と読める。今回の修正では変更せず、文言整理の
  要否を別途判断する。
- **`gold_confirmed` の既存欠落**。`*-explicit-multifile` が両条件で 3/3 失敗。
  根は「親が `confirmed:` 項目の引用元を絶対パスで書かない」ことにある
  （変更前後12実行で絶対パス付き項目は0件）。本プランとは独立した課題として
  切り出し済み。
- **このスイート自体の非決定性**。変更前後どちらも失敗の顔ぶれが周ごとに
  入れ替わり、`direct` モードですら周によって落ちる。現状では
  「3周での再現回数」でしか判定できず、単発の失敗数比較は意味を持たない。
  リリースゲートとして機能させるには、まずこの安定性に手を入れる必要がある。
