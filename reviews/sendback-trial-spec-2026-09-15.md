# 差し戻しの小規模実機検証 仕様（2026-09-15、実施前）

`reviews/sendback-scope-2026-09-15.md` の保存済みデータ評価を受けて、
**実装前に**実機検証の仕様を固める。本稿は仕様のみで、
フック実装も課金測定もまだ行わない。

## 0. 目的と非目的

**目的**: 差し戻しが実機で成立するかを、最小の実行数で観測する。

**非目的**:

- 回復率の推定値を出すこと。この規模では区間が広すぎて意味を持たない。
- 改善の有無を結論づけること。今回は**動作の観測**であり、効果測定ではない。
- 破棄経路の発生率を出すこと（§4.4）。

## 1. 差し戻し対象の限定

差し戻しを送るのは、**判定可能な親の保持違反**に限る。
`retention_checks.run_all` の結果が次を**すべて**満たす場合だけ block を返す。

| 条件 | 値 |
|---|---|
| 子出力 | 取得できている（`child_texts is not None`） |
| `check_child_items` | `ok`（使える絶対パス付き項目が1件以上） |
| `check_line_retention` | `violation` |
| 最終回答 | 特定できている（`final_answer` の `status == 'ok'`） |

いずれかが `undetermined` の場合、および `check_child_items` が
`violation`（子側の欠落）の場合は **block を返さない**。
取得不能・ファイル消失・子の欠落を親に差し戻すと、正しい回答を壊す側に回る。

保存コーパスでこの条件に当たるのは 456件中 308件（`sendback-scope` §1）。

## 2. 事前確認（課金前の必須手順）

1. 専用チェックアウト（detached worktree）を作り、測定するコミットに固定する。
2. そのチェックアウトで `python3 evals/compare/judge.py --selftest` を通す。
3. `evals/compare` のテストと `./evals/run.sh` を通す。
4. フックが**実行ごとに自分の呼び出しを記録**することを、合成セッションで確認する。

この4点が揃うまで課金実行に進まない。

## 3. 検証構成

| 項目 | 値 |
|---|---|
| ケース | `auto-explicit-multifile`、`compare-explicit-multifile` |
| モード | haiku / sonnet / auto（委譲3モード。direct は `gold_confirmed` 対象外） |
| 条件 | フック無し（対照）／フック有り |
| 周回 | 2 |
| 実行数 | 2ケース × 3モード × 2条件 × 2周 = **24** |
| 費用見積り | 対照12実行 ≈ $2.0、フック有り12実行 ≈ $2.0＋差し戻し分。合計 **$4 前後** |

費用は `sendback-scope` §4 の復元単価による参考推定で、上限保証ではない。
対照条件を同数取るのは、追加ターン数と費用の差分を**同一条件で**取るため。

## 4. 観測項目

フック側と transcript 側の両方から取り、片方でしか取れない項目は明示する。

### 4.1 block 要求後に親が再開したか

- 判定源: block を返した時刻以降に、親 transcript へ
  新しい assistant エントリが追加されたか。
- 値: `resumed` / `not_resumed`。
- フック側には「block を返した」事実と、その時点の transcript 行数を記録する。
  再開の有無は行数の増加で判定し、推測で埋めない。

### 4.2 再開後に全行を保持したか

- 判定源: 再開後の最終回答に対して `retention_checks.run_all` を再実行。
- 値: `ok`（全行保持）／`violation`（残存欠落あり。欠落行数も記録）／
  `undetermined`。
- 差し戻し前後の `kept` / `altered` / `dropped` を**行単位で**並べて記録する。
  「直った」ではなく何行戻ったかを残す。

### 4.3 追加ターン数と実測費用

- 判定源: `result` イベントの `num_turns` と `total_cost_usd`。
- 値: フック有りと対照の**同一ケース・同一モードの差分**。
- 周回ごとのばらつきも残す。n=2 なので平均値は代表値として扱わない。

### 4.4 再ブロック上限に達した場合の終了状態

- 判定源: フック側の block 回数記録と、`stop_hook_active` が真で
  成功を返した回数。
- 値: 上限到達の有無、到達時の最終回答が `violation` のまま終わったか。
- 上限は既定のまま測る。`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` は動かさない。

## 5. 再開しなかった場合の扱い

`not_resumed` を観測したとき、その原因を**破棄経路と断定しない**。

CLI は tool result／MCP end-turn／loop tick で終わったターンの Stop ブロックを
破棄するが、フックの記録と transcript だけでは、再開しなかったのが
破棄なのか別の理由なのかを区別できない。区別する材料が無い実行は
**`原因不明`** として残す。

| 観測 | 記録する値 |
|---|---|
| 再開した | `resumed` |
| 再開せず、破棄を示す直接の証跡がある | 証跡とともに記録 |
| 再開せず、識別材料が無い | **`原因不明`** |

`原因不明` は破棄経路の件数にも、フックが効かなかった件数にも数えない。

## 6. 記録の形

1実行1行で次を残す: ケース、モード、条件、周回、block 送出の有無、
`resumed` / `not_resumed` / `原因不明`、差し戻し前後の保持行数、
`num_turns`、`total_cost_usd`、block 回数、上限到達の有無。

集計は**実行単位**で出し、割合を書く場合は必ず分母を併記する。
n=24（うちフック有り12）では、観測された事象の**有無**までしか言えない。

## 7. 中止条件

次のいずれかに当たったら、周回を終えずに中止して報告する。

- 差し戻しが**正しい回答を壊した**（差し戻し前に `ok` だった実行で block が出た、
  または再開後に保持行が減った）。
- 判定不能な実行に block を送っていた。
- 対照条件の費用が見積りの2倍を超えた。

## 8. 本稿の位置づけ

実装・課金測定は保留のまま。本稿が固めたのは、実施するときの
**対象の限定・観測項目・原因不明の扱い・中止条件**であり、
実施の可否そのものは別の判断である。
