# 計画フェーズの形で routing が効くかの検証・事前登録（2026-09-18）

`reviews/parent-no-read-rate-2026-09-17.md` と
`reviews/parent-no-read-shape-2026-09-17.md` の続き。
**走らせる前に本記録をコミットする。**

## 1. 何を確かめるのか

漏れ率 21.7% を出した `auto-explicit-multifile` の `prompt_delegate` は、
**委譲を指示していない。**

```
After a User is created, what happens? The relevant paths are {FIX}/... .
Name the concern and the job.{WMHINT}
```

`wm_hint` も「**If** you delegate reading to a worker, use --worker-model {WM}」
という条件文である。suite B は `cases.json` の定義どおり
「**product auto routing**」、つまり**親が自分で委譲を選ぶか**を測っていた。

`parent-no-read-shape-2026-09-17.md` §1 の内訳は、この読み方と整合する:

| | agents=0 | agents≥1 |
|---|---|---|
| FAIL | 6 | 7 |
| pass | 0 | **47** |

**pass した 47 arm は全て委譲している。FAIL の半分近くは一度も委譲していない。**
**つまり測っていたのは「委譲の質」ではなく「委譲を始めるかどうか」である。**

SDD（SuperPowers の `writing-plans` → `executing-plans`）の計画文書は、
**読み取りの委譲を文書の制約として書く。** ここが違う。

## 2. 測る問い

**計画文書の形をした prompt は、bare な prompt で出た
「親が委譲せずに自分で読む」を減らすか。**

**両腕は同じファイル・同じ問いで、prompt の書式だけが違う。**

## 3. 設計

### 3.1 corpus と対象ファイル

**Django 5.2.1、コミット `bc833e8883db4a333a6485d91637b78c85e2b13b`**
（`DJANGO_ROOT`。dose 測定と同じ固定点なので並べて読める）。

| ファイル | サイズ B | 行 | フックの判定 |
|---|---|---|---|
| `django/core/management/__init__.py` | 17,407 | 442 | **deny**（442/350 行） |
| `django/core/management/base.py` | 24,771 | 707 | **deny**（707/350 行） |
| `django/core/management/commands/migrate.py` | 21,349 | 508 | **deny**（508/350 行） |

**合計 63,527 B。上の数値は固定コミットの checkout で実測した。**

**3 ファイルにした理由は 2 つある。**

1. **単一委譲の契約（1 回あたり最大 3 パス）に収まる。**
   4 件以上はバッチ判断が入り、本測定の問いと無関係なばらつきが増える。
2. **1 run が安い。** §4 のとおり枠が $21.6 しかなく、
   ファイルを増やすと N が落ちる。**N のほうが優先である。**

### 3.2 これは「deny が出る世界」である（前回との最大の違い）

`parent-no-read-shape-2026-09-17.md` §2 は、21.7% を出した case の
`user.rb` が **22,546 B** に縮んでおり、**deny が原理的に出ない**ことを
突き止めた。あの率は「**条文だけが根拠の世界**」の率だった。

**本測定の 3 ファイルは、いずれも行数閾値を単独で超えて deny する。**
**条文と機構の両方が働く条件で測る。**
**この差があるので、21.7% を本測定の対照として引用しない**（§3.3）。

### 3.3 対照は過去の数字ではなく、同時に走らせる腕である

**21.7% は case も fixture サイズも corpus も違う。** 対照に使えない。
**同じファイル・同じ問いで、prompt の書式だけを変えた 2 つの case を、
同じ巡回で走らせる。**

| case | prompt の書式 | 役割 |
|---|---|---|
| `django-plan-trace-bare` | suite B と同じ形（パスを挙げるだけ、`wm_hint` は条件文） | **対照** |
| `django-plan-trace-plan` | 計画文書の形（目的・制約・手順。**本文を自分の context に入れるなと書く**） | **処置** |

**どちらも `modes: ["auto"]` とする。** `modes: ["auto"]` と `isolation` 無しは
`cases.json` に 14 件ある既存の書式である。

### 3.4 処置腕は道具の名前を出さない（ここが設計の要）

**`token-shunt:bulk-reader` と書いてしまえば、従うのは当たり前である。**
`redmine-visible-scope` の `prompt_delegate` は道具を名指ししており、
dose 測定の auto 腕は 88/88 で本文 0 バイトだった。
**それを測り直しても何も分からない。**

**SuperPowers の計画文書は道具を名指ししない。** 書くのは制約である。
したがって処置腕の prompt は**制約だけを書き、道具名を出さない**:

> **Goal:** 下記 3 ファイルにまたがる呼び出し経路を、実装計画を書ける粒度で
> 明らかにする。
> **Constraints:** これは計画フェーズであり、編集はしない。
> **ソースの本文を自分の context に入れないこと。読み取りは worker に委譲し、
> 手元には結論だけを残す。** worker を使う場合は `--worker-model auto`。
> **Steps:** (1) 3 ファイルの読み取りを委譲する (2) 返ってきた事実から経路を
> 組み立てる (3) 各段の関数名と定義 file の絶対パスを挙げる

**対照腕の prompt:**

> `manage.py migrate` が実行されてから `MigrationExecutor` が生成されるまでの
> 呼び出し経路を追え。関係するパスは {FIX}/… の 3 件である。
> 各段の関数/メソッド名と、それが定義されている file の絶対パスを挙げよ。
> If you delegate reading to a worker, use `--worker-model auto`.

**問いの本体（何を答えるか）は両腕で同一にする。** 差は書式だけである。

### 3.5 処置は束であって、分解ではない

処置腕は「計画文書の register」と「本文を context に入れるなという明示制約」を
**同時に**変えている。**この 2 つを本測定は分離しない。**
**分離しない理由は、SDD で実際に出荷される形がこの束だからである。**
効果が出ても「どちらが効いたか」は言えない。§8 に再掲する。

### 3.6 正答（`gold`）

固定コミットで実地に確認した。**各 token は 3 ファイルのどれかに固有に紐づく。**

| token | 定義場所 |
|---|---|
| `load_command_class` | `django/core/management/__init__.py:42`（この 3 件では固有） |
| `run_from_argv` | `django/core/management/base.py:399` |
| `MigrationExecutor` | `django/core/management/commands/migrate.py:114` で生成 |

経路そのもの（参考、答え合わせ用）:
`ManagementUtility.execute`（`__init__.py:353`）→ `fetch_command`（`:246`）
→ `load_command_class`（`:42`）→ `BaseCommand.run_from_argv`（`base.py:399`）
→ `BaseCommand.execute`（`:435`）→ `Command.handle`（`migrate.py:97`）
→ `MigrationExecutor(...)`（`migrate.py:114`）。

**`gold` は 3 件すべて必須**（`gold_any` ではない）。
**3 ファイルを横断しなければ揃わないようにするためである。**

## 4. N と枠

**総枠 $150。累計 約 $128.4（`parent-no-read-rate-2026-09-17.md` §0）。
残り 約 $21.6。**

**本段階の上限 $21**、見込み **$18**。

1 run の見積り: Django dose の auto 腕は 1 ファイルで中央値 $0.09〜$0.21。
本測定は 3 ファイル 63 KB で、**対照腕が漏れた run は親が 63 KB を飲む**。
**$0.22/run** と見る（80 run で $17.6）。

**reserve は $0.80。** django-dose の最高 1 run $0.6721 に、
ファイルが大きくなった分を足した。
**平均ではなく最大から取る**（メモリ `billable-stop-rule-needs-a-mechanism`）。

**run ごとに `spend.py --cap 21 --reserve 0.80` を通し、exit 3 で抜ける。**

### 4.1 N = 各腕 40（80 run）と、その検出力

**Fisher 正確検定（両側 α=0.05）の検出力を、走らせる前に出しておく**
（4,000 反復のシミュレーション、`Random(20260918)`）:

| 対照 | 処置 | n=30/腕 | n=35/腕 | **n=40/腕** |
|---|---|---|---|---|
| 0.30 | 0.05 | 0.63 | 0.74 | **0.82** |
| 0.22 | 0.05 | 0.31 | 0.41 | **0.51** |
| 0.30 | 0.10 | 0.36 | 0.46 | **0.53** |
| 0.22 | 0.10 | 0.14 | 0.19 | **0.23** |

**n=40/腕で 0.8 を超えるのは、いちばん都合のよい 1 行だけである。**

**したがって「有意でなかった」を「差が無い」と書けない。**
§6 に、そのときの書き方を先に決めておく。

**枠に達したらそこまでで報告し、後から足さない。**
**2 つの case を交互に回すので、どちらも同じだけ欠ける。**

## 5. 解析（走らせる前に固定する）

**主要: `parent_no_read` の FAIL 率を 2 腕で比べる。Fisher 正確検定（両側）。**

**予測: 対照 ≈ 0.30、処置 ≤ 0.05、p < 0.05。**
（対照の 0.30 は `parent-no-read-rate` の auto mode の点推定を借りた見込みであって、
**対照群は今回同時に取るので、この数字を解析に使わない。**）

**副次、すべて事前に決めたもの:**

1. **`agents=0` の run 数を両腕で。** `parent-no-read-shape` §1 が特定した
   機構そのものである。**主要が動いたとき、それが「委譲を始めた」ことで
   説明できるかを見る。** 検定はしない。
2. **両腕の Wilson 95% CI。** 点推定だけ書かない。
3. **`parent_read_bytes` の中央値を両腕で。** 0 でない run は
   **中身を分類する**（フックの拒否文か、corpus の本文か）。
   dose 測定の教訓どおり、拒否文も `parent_read_bytes` に数えられる。
4. **`accuracy`（`gold` 3 件すべて）を両腕で。**
   **処置腕が委譲した結果、正答が落ちていないかを見る。**
   委譲しても答えられないなら、遵守率が上がっても意味がない。
5. **1 run の実費の中央値を両腕で。** 検定しない（§8 参照）。
6. **`child_no_body` の失敗件数と理由（フェンスを含む）。記録するだけ。**

**中間解析はしない。** 走行中に見るのは **run 数と spend だけ**とし、
`parent_no_read` の内訳は**全 run 終了後に一度だけ**集計する
（`parent-no-read-rate` §5 と同じ扱い）。

**採点は `pairs.py` が出す行に対して行う。書き捨ての採点器を作らない。**

## 6. 予測を外したときにどう書くか（事前に決める）

- **p < 0.05 かつ処置 < 対照** なら、
  「**計画文書の形は、この case で routing の漏れを減らした。**」
  **「SDD なら直る」とは書かない。** case は 1 つ、問いの形は 1 つである。
- **p ≥ 0.05** なら、「**差を検出できなかった。**」と書く。
  **§4.1 の表を併記し、検出力が足りていない可能性を明示する。**
  **「差が無い」とは書かない。**
- **処置腕でも漏れが出た**なら、その run の形を
  `parent-no-read-shape` と同じ分類で**数だけ**報告する。
  **形の分析は $0 の事後探索として別記録にし、本記録に混ぜない。**
- **対照腕の率が 21.7% と大きく違った**場合、
  **`parent-no-read-rate` の記録は書き換えない。並べて残す。**
  違いは fixture が deny を出すかどうかで説明がつく（§3.2）ことを書く。

**ここに書いた閾値と文言は今決めている。後から動かさない。**

## 8. 事前に認めている弱点

- **費用の問いには答えない。** 本測定に `direct` 腕は無い。
  **「計画フェーズの用量で auto が direct より安いか」は未解決のまま残る。**
  §5 副次 5 は 2 つの auto 腕どうしの比較にすぎない。
  **これは遵守率を主要に選んだことの代償であって、見落としではない。**
- **処置は束である**（§3.5）。計画文書の register と明示制約を分離しない。
- **検出力は都合のよい 1 点でしか 0.8 に届かない**（§4.1）。
- **case は 1 つ、問いの形は 1 つ、corpus は 1 つ、言語は 1 つ。**
- **ファイルの選択は私が行った。** 3 件とも行数閾値を超えるものを選んだ。
  **これは意図的だが、Django の代表値ではない。**
- **`gold` が厳しすぎる可能性がある**（2026-09-18 追記、走行前）。
  `load_command_class` は経路の一段だが、親が `fetch_command` や `execute` を
  挙げて**この名前だけ落とす**ことはありうる。その場合 **§5 副次 4 の
  `accuracy` は両腕で落ちる。** 主要（`parent_no_read`）には影響しないが、
  **「委譲しても答えられたか」は言えなくなる。**
  **gold は緩めない。** 緩めれば「3 ファイルを横断しないと揃わない」という
  §3.6 の設計が崩れるからである。**§10.1 でも確認しない**
  （それは副次 4 を先に見ることになる）。**落ちたらそう報告する。**
- **編集を含まない。** v0.1 は deny 対象ファイルの編集を範囲外と明記しており
  （`check-file-size:151`）、**実装フェーズの適合性は本測定の範囲外である。**
- **eval の case であって、実際の SDD 利用の標本ではない。**
- 費用も挙動も**今日のモデル価格・今日のモデル**に依る。

## 9. 残すもの

**run ディレクトリを消す前に**

```
python3 evals/compare/pairs.py -o reviews/data/plan-phase-routing-2026-09-18.csv \
    --min-rows 80 <runs>
```

**`--min-rows` を必ず付ける**（2026-09-18 追記、走行前）。
`pairs.py` は **0 行でも exit 0** で、CSV にヘッダだけを書く。
`pairs.py && rm -rf <runs>` と書けば、**1 行も保存できていないのに削除が走る。**
枠で打ち切られて 80 対に届かなかった場合は **exit 3 で止まり、
そこまでの行は書かれている**ので、期待値を下げて取り直す。

（メモリ `keep-per-pair-rows`。88 対を一度失っている。）

**`pairs.py` は片腕の case でも行を出す**（`cf88864`）。
**本測定は両 case とも 1 腕なので、この修正に依存する。**
**走らせる前に、片腕 case で行が出ることを実データで確認する**（§10 の 5）。

### 10.1 最初の 1 対では機構だけ確認する

**この case を走らせた実績が無い。** 各腕 1 run を終えた時点で、
**次の 4 点だけ**を見る:

1. verdict が evidence 不足の ERROR になっていないか。
2. **対照腕で 3 ファイルとも deny が出ているか**（§3.2 の前提。
   出ていなければ測っている世界が違う）。
3. 1 run の実費が §4 の reserve $0.80 に収まっているか。
4. `pairs.py` が両 case の行を出しているか。

**結果の中身（どちらの腕が漏れたか、正答したか）は見ない。**
**崩れていたら止めて、何が違ったかを記録してから設計をやり直す。**
