# 固定 N の送り戻しプローブ 設計（2026-09-16、事前登録）

`reviews/sendback-registration-decision-2026-09-15.md` §7 が次に置いたもの。
**本記録は設計だけで、実行していない。追加課金は発生していない。**
走らせるのは指示が出てからで、そのときは本記録を**先にコミットした状態**で走らせ、
結果は本記録の事前基準にそのまま突き合わせる（走らせてから基準を決めない）。

## 1. 埋める穴

登録判断 §4 の限界のうち、まだ埋まっていないのは次の 2 点である。

- 出荷構成（送り戻し **on**）がスイート単位で未測定。実機の根拠は
  親側 12 run / 2 ケース、子側 4 run / 1 ケース、いずれも 1 マシン・1 CLI ビルド。
- 破棄経路（tool result などで終わったターンの block 破棄）の発生率が不明。

埋めないもの（このプローブの対象外、理由つき）:

- 再 block 上限の終了状態は `sendback-unobserved-2026-09-15.md` §1 で実測済み。
  製品フックは `stop_hook_active` で見送るため構造上到達しない。
- 子側の欠落・子出力取得不能は登録で直らないと §4 が結論済み。

## 2. 比較 A/B にはしない

対照（off 条件）を置かない。理由は 2 つ。

1. **意味のある対照が高い。** A スイートの 19→16 はモデル揺れだった
   （`reviews/a-suite-failures-9346d19-2026-09-16.md`）。合否のペア比較で
   送り戻しの効果を出すには、その揺れを上回る組数が要る。
2. **対照なしで答えられる。** フックがある run に影響できるのは、その run で
   **block を出したときだけ**である。block を 1 件も出していない run が落ちても、
   それはフックのせいではない。この排除は各 run の試行ログで機械的に判定できる。

したがって主要評価項目は「block が出たとき直ったか」という**条件つき**の量であり、
「送り戻しがスイートの合格率を上げるか」ではない。後者は測らない、と明記する。

## 4. ケース選定（保存済みトランスクリプトから、課金なし）

`9346d19` の A/B 77 本のうち bulk-reader の戻りがある 26 本に対し、
`sendback_retention.run_all()` をオフラインで当てた結果が選定根拠である。

| 判定 | 件数 |
|---|---|
| 親の `line_retention` = violation（＝ Stop の block 候補） | **10 / 26** |
| 同 ok | 13 / 26 |
| 同 undetermined | 3 / 26 |
| worker 側 `child_items` = violation（＝ SubagentStop の block 候補） | **4** |

送り戻しを **off** で走らせた測定に、これだけの block 候補が残っている。
とくに `compare-explicit-multifile/haiku` は
`reviews/a-suite-failures-9346d19-2026-09-16.md` §1 の

選ぶ 8 枠（ケース × モード）と、`9346d19` での実測費用:

| 枠 | 候補 | 実測 $ |
|---|---|---|
| compare-hook-deny-route / auto | 親 | 0.0841 |
| compare-explicit-multifile / haiku | 親（gold と同一 run） | 0.1138 |
| compare-explicit-multifile / sonnet | 子 | 0.1473 |

`auto-bulk-facts/auto`（$0.69）と `/sonnet`（$0.49）は外した。費用が枠 4 つ分あり、
かつ isolation の別件失敗を抱えていて、送り戻しの観測が濁るためである。

したがって block 件数の期待値は母集団の発生率ではなく、
P1・P2 は「block が出た条件での修復率」としてのみ読める。

## 5. 固定 N

**N = 24 run（8 枠 × 3 周）。**

固定するのは **run 数**であって block 数ではない。block 数を固定すると
「出るまで回す」適応的停止になり、修復率が上に歪む。
block が予想より少なければ「違反が再現しなかった」が結論であり、
**追加で回さない**。多ければ多いまま報告する。

到達しうる精度（Wilson 95%）:

| 観測 | 下限 |
|---|---|
| 12/12 全部修復 | 0.76 |
| 11/12 | 0.65 |
| 既存 6/6（親）＋ 3/3（子）＝ 9/9 | 0.70 |
| 9/9 に 12/12 を足した 21/21 | **0.85** |

S1・S4 が 0 件だった場合の上限はルール・オブ・スリーで 3/24 = **0.13**。
「誤 block は起きない」とは言えず、「24 run では起きなかった」までである。

## 6. 実行条件

- **課金前点検**（`billable-measurement-preflight`）: 専用チェックアウトを
  コミットに固定し、生成物以外の差分なしを確認し、**そのチェックアウト内で**
  `judge.py --selftest` を通す。固定コミットを結果と一緒に報告する。
- 条件: `SENDBACK=on`。`cases.json` は変更しない（恒常費用を増やさないため）。
- 3 周は**続けて回さず**、周ごとに試行ログを保存する。モデル揺れが周に相関しても
  分離できるようにするためである。
- CLI 版を記録する。フックは毎回 `cli_version` を書くので追加作業はない。

既定の挙動を変えない小さな差分 3 点。いずれもテスト先行で入れた。

2. `evals/compare/run.sh`: `MODES` 環境変数でモードを絞れるようにする

### 7.1 枠の指定（2026-09-16 追記、`cfe00b1` の後）

§4 の 8 枠は**ケース×モードの組**だが、`ONLY` と `MODES` は直積である。
`ONLY` に `auto-bulk-facts` を入れると、費用を理由に外した `/auto`（$0.69）と
`/sonnet`（$0.49）まで課金される。1 周あたりの選択肢は 3 つあった。

| 案 | 1 周の余分 | 3 周の余分 | 備考 |
|---|---|---|---|
| `ONLY` × `MODES` の直積 | $1.29 | **+$3.87** | 外した 3 枠が毎周入る。`auto-bulk-facts/auto` は isolation の別件失敗を持ち込む |
| 枠ごとに run.sh を起動（1 周 8 起動） | $0.41 | **+$1.09** | runner 自身のプローブ 2 本が 8 倍（$0.052 × 24 起動） |
| `SLOTS=id/mode,…` を足す | $0 | **$0** | 1 周 1 起動のまま、8 枠だけを回す |

**`SLOTS` を採る。** 直積案は見積もりをほぼ倍にし、しかも意図的に外した枠を
戻してしまう。起動分割案は測定内容は正しいが、プローブ費用が §9 の見積もりの
8 倍になる。`SLOTS` は run.sh のフィルタ 1 つで、既定（未設定）では挙動が変わらない。

実装済み（テスト先行、`test_runner.py` に 3 件）:

- `SLOTS` 未設定なら従来どおり `ONLY`/`SUITE`/`MODES` だけで選ぶ。
- 設定時は planned とループの両方を `case/mode` で絞る。並び順はカタログ順で、
  `SLOTS` の並びではない。
- **宣言のない枠が 1 つでもあれば起動前に落とす**（`unknown_slots`）。
  `auto-small-files/opus` のような綴り違いが、事前登録より小さい集合を
  黙って課金することを防ぐ。これが `SLOTS` を足す主な理由でもある。

### 7.2 S3 の出所（同日）

`sendback_probe.py` は S3（`not_resumed`）を、フックが記録した `baseline` と
**評価用トランスクリプト**の突き合わせで出していた。フックの `baseline` は
CLI の**セッションファイル**（記録の `transcript_path`）を数えたものであり、
評価用トランスクリプトは CLI 標準出力の stream-json で行の集合が違う。
別ファイル同士を比べていたので、S3 は 0 にも 1 にも寄りうる。

記録が名指すセッションファイルを読む形に直した。セッションが手元に無いときは
**0 ではなく `s3_unmeasured`** に数える。「再開しなかった実行は無かった」は
測れていないときに言ってよい言葉ではないためである。テストは
`test_sendback_probe.py` に 2 件（測れないときの扱い、記録が名指す出所）。

### 7.3 P1 は完了後の再判定でしか測れない（同日）

実物のフックに合成の Stop 入力を与えて端から端まで通したところ、
**P1 が構造上 0 にしかならない**ことが分かった。`sendback_probe.py` は
「後続の Stop 記録で `line_retention` が ok になったか」で修復を数えていたが、
差し戻しに答えたターンの終わりは必ず `stop_hook_active` で届き、
フックは**何も計算せずに見送る**。実際の記録は次のとおりで、`checks` が無い。

```
blocked            | checks: {'child_items': 'ok', 'line_retention': 'violation'}
reblock_suppressed | checks: None
```

§3 は P1 の出所を初めから「試行ログ + **再判定**」と書いていた。実装が
それをしていなかった。完了後のセッションから `check_inputs()` +
`run_all()` で最終回答を判定し直す形に変えた。P2 も同様に、block された
worker の **その worker の**最終報告を `check_child_items()` で見る。
セッションが無ければ 0 ではなく `p1_unmeasured` に数える。

P1 の分母は **block ではなく run** である（1 つの回答は直ったか直っていないかの
どちらかで、block 2 回で 2 件にはならない）。P2 の分母は worker である。

実物のフックが書いた試行ログでの確認:

| 完了後のセッション | P1 |
|---|---|
| 親が該当行を書き直している | 1 / 1 |
| 親が落としたまま | 0 / 1 |
| セッションが手元に無い | 0 / 1（`p1_unmeasured` 1） |

テストは `test_sendback_probe.py` を 4 件差し替え・追加した。差し替えた 2 件は
**フックが出しえない記録**（`checks` 付きの `reblock_suppressed`、
worker を取り違えた P2）を前提にしていたので、通っていても意味がなかった。

`SLOTS` についても、planned だけでなく**ケースループまで届くか**を
CLI ダブルで確認するテストを足した（`test_runner.py`）。

走らせるときの形（1 周 1 起動、3 周）:

```sh
SENDBACK=on SLOTS=compare-hook-deny-route/auto,compare-explicit-multifile/haiku,\
compare-explicit-multifile/sonnet,compare-edit-dense-lines/auto,\
reader-batch-ambiguous/auto,reader-bounds/auto,auto-bulk-facts/haiku,\
auto-routing-boundary-known-range-deny/auto bash evals/compare/run.sh
```

## 8. 合否の読み方（事前に決める）

- **S1 または S4 が 1 件でも出たら、出荷構成の欠陥**として扱う。修復率は見ない。
- P1 が 12/12 近辺なら、§4 の「12 run / 2 ケース」の限界は
  「24 run / 8 枠」に広がる。一般的な回復率にはならない。
- P1 に失敗が混ざったら、`not_resumed` と「再開したが回復不完全」を分けて数える。
  前者（S3）を**破棄経路の観測として数えてはならない**。破棄を示す直接の証跡が
  同じ実行にある場合だけ証跡とともに記録し、無ければ `原因不明` として残す
  （`sendback-trial-spec-2026-09-15.md` §5）。破棄の発生率は、このプローブでは
  依然として出ない。
- block が 3 件未満だった場合は **判断保留**とし、N を増やさずに
  「off 条件で見えた違反が on 条件で再現しなかった」と記録する。

## 10. 限界（走らせても残るもの）

- 1 マシン・1 CLI ビルド。§4 のこの限界は N では埋まらない。

  block 件数の予告ではない。
