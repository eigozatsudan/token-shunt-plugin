# 実行前チェックの行き過ぎを塞ぐ（2026-09-17）

`reviews/pairs-tool-trial-2026-09-17.md` §3 で実測した超過への対応。**課金なし。**

## 1. 何が起きていたか

4 対の道具試験で、見積り **$1.0** に対し **$1.0868**（8.7% 超過）を使った。

**ガードは正しく動いていた。** `spend.py --cap 1.0` は run の**前**に残高を見る。
3 本目の後の残高は $1.0 を下回っていたので 4 本目は許可され、その 4 本目が枠を越えた。

**これは実装ミスではなく、実行前チェックの構造そのものである。**
run の前にしか見ないガードは、**必ず 1 run 分だけ行き過ぎうる。**
`$30 → $36.55` のときと違い、今回は仕組みが無かったのではなく、
**仕組みの粒度が 1 run だった。**

## 2. 直したこと: `--reserve`

```
spend.py --cap 40 --reserve 0.55 <dir> ...
```

**`--reserve` は「次の 1 run が使うと見込む額」。**
`残高 + reserve >= cap` で止める。**止まりが 1 run 早くなる**
——実行前にしか見られないチェックが正確になれる唯一の位置である。

**reserve は最近の最も高い 1 run から取る。平均ではない。**
高い側の尾を外した平均こそ `$30 → $36.55` の原因だった
（メモリ `billable-stop-rule-needs-a-mechanism`）。

### 2.1 決めたこと

- **`--reserve` 単独は usage error。** reserve だけでは何も決まらないので、
  黙って無視すると**「止まる仕組みを頼んだ」という誤解だけが残る。**
- **境界（`残高 + reserve == cap`）では止める。** 素の cap が
  「cap ちょうどで止める」なので、揃えた。
- **何も使っていなくても、1 run が単独で枠を越えるなら止める**
  （`--cap 0.2 --reserve 0.25` → 即 stop）。**始めること自体が誤りだから。**
- **stdout の数字は変えていない。** 出るのは**使った額**であって
  `残高 + reserve` ではない。reserve は終了コードだけを決める。
  記録に残る数字を動かしてはならない。

## 3. テスト（9 件。**実装より先に書いて RED を確認した**）

reserve が 1 run 手前で止める / まだ収まるなら 0 / **境界で止まる** /
**未使用でも単独超過なら止まる** / **stdout は使った額のまま** /
オプションの順序は任意 / **cap 無しの reserve は usage error** /
数値でない・0・負は usage error / 値が無いのは usage error。

## 5. 残る限界

- **reserve は見積りである。** 実際の 1 run がそれより高ければ、やはり越える。
  **保証ではなく、粒度を 1 run から「見積りの誤差」へ縮める仕掛けである。**
- run の**途中**で止める手段は無い。1 run 分の不確かさは消えない。
