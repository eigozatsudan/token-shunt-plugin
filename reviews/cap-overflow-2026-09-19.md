## 0. 先に書くこと

**1. 直らなかった。** `child_msg_cap` の失敗率は
control **19/39 = 0.487**、treated **14/39 = 0.359**、
Fisher 両側 **p = 0.35942**。**差は決まらない。**
設計 §6-3 の「何も動かなかった」に該当する。
**契約文 1 規則では直らない**、というのが本ブロックの答である。

**2. 介入の機構は一度も発火しなかった。**
treated 39 run のうち `stop_reason: cap_reached` を返した run は **0 件**。
`status: partial` も treated **1/39** で、control **2/39** より**低い**。
設計 §5-2 は「効いているなら partial は上がるはず」と書いた。**上がっていない。**
**規則は読まれた形跡が無い。** 率が動かなかったのではなく、
**そもそも規則が使われなかった。**

**3. 盲検は失われている。**（§7.2.2）
`--runs` の取り違えで止まった理由を調べる過程で、driver のログの
`FAIL ... child_msg_cap: agent result NNNN chars > 4000` を読んだ。
**control 4 件・treated 2 件の失敗と、その文字数を見ている。
これは主要指標そのものである。**
以降の判断が盲検下で行われたとは主張しない。

**4. 最初の 20 run は交互ではない。**（§7.2.1）
control 10 → treated 10 の順で走った。**時刻と腕が相関している。**
継続分（各腕 +29）は 5/5 交互に戻したが、**最初の 10/腕は戻せない。**

**5. control の率が事前の想定から大きく外れた。**（§6-4）
§1 は 22/77 = 0.286（Wilson [0.197, 0.395]）を前提に置いたが、
本ブロックの control は **0.487（Wilson [0.339, 0.638]）** で、
**その区間の外である。** 以下、control は**本ブロックの 39 run のみ**を
control として読む。**検出力の計算（§4.1）も前提が外れている。**

**accuracy は落ちていない。** 両腕 **0/39 失敗**。
§6-1 の「上限は守らせたが答えが痩せた」ではない。
**痩せてもいないし、守られてもいない。**

## 4. 何が言えて、何が言えないか

**言える:**

- **`plugin/agents/bulk-reader.md` に「切ってよい」と 1 規則足しても、
  超過率は動かなかった。** p = 0.359、n = 39/腕。
- **worker はその規則を使わなかった。** `cap_reached` が 0 件である。
- **超過は accuracy の問題ではない。** 両腕とも 3 語は揃う。
  `reviews/child-msg-cap-2026-09-18.md` の「漏れではない」を、
  **今度は control を自前で持った状態で再確認した。**
- **閾値下 regime の超過率は 0.286 より高い。** 本ブロック単独で 0.487。
  4 ブロックの寄せ集めより、**同一条件 39 run のほうが信用できる。**

**言えない:**

- **「契約文では直らない」は 1 通り分の証拠でしかない**（§8-4）。
  試した書き方は 1 つである。
- **部分的な改善があったかどうかは分からない**（§8-2）。
  0.487 → 0.359 は、この n では区別できない。
- **他の課題形でどうかは分からない**（§8-3）。
  絶対パス付きの列挙という、**上限に最も厳しい 1 つの形**でしか測っていない。
- **`--runs` の取り違え以前（$4.8259 / 20 run）の分**は
  この 78 run に含まれている。**別集計はしていない。**
  §7.2 の通りデータは健全（`errors=0`、run ディレクトリ全残存）である。

## 5. 次にやるなら

**契約文の側ではない。** 本ブロックが示したのは、
**worker が上限を認識していながら規則を使わない**という形である。

runtime 側（返答が上限を超えたら worker に送り返す）が次の候補だが、
**本ブロックはそこまで言わない**（設計 §6-3 の通り）。
**残高（上限 $200 に対し累計 約 $190.3）でも、次のブロックは組めない。**

`capfix` ブランチ（契約文の変更、`77ef7b1`）の扱いは**別途決める。**
**「超過率を下げた」という根拠には使えない。**
ただし**悪化もしていない**ので、
「上限を超えるときの逃げ道が契約に無い」という §1.1 の指摘自体は残る。
