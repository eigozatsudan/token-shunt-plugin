# 再発（言い直したあと短い締めで落とす）を高頻度で作る装置の設計（2026-09-16）

`reviews/sendback-rescue-2026-09-16.md` §6.5 が残した課題。
**本記録は設計だけで、実行していない。追加課金は発生していない。**
走らせるのは指示が出てからで、そのときは本記録を先にコミットした状態で走らせる。

## 1. 何を作るのか

塞いだ死角（`3517831`）はこういう形だった。

1. 親が行を落とす → Stop が block する
2. 親が**全行を言い直す**
3. 親が**そのあとさらに短い締めの 1 通**を出す
4. その 1 通が run の最終結果になり、行は消えている

30 run に 1 件しか出ていない。**このままでは修正の実機確認に $50 規模かかる。**
必要なのは「この 4 段を高頻度で起こす構成」である。

装置は**製品の推奨構成ではない**。腕 B（リマインダ抜き）と同じく、
特定の失敗を意図的に量産するための実験用の組み立てである。

## 2. 機構の仮説（どれを操作すれば頻度が上がるか）

- **H1 block 文面**: 今の `block_reason` は
  「… Restate every line below verbatim, each on its own line, **before you finish**:」
  で終わる。**「終える前に言い直せ」は「言い直してから締めろ」と読める。**
  4 段目を誘っているのは、送り戻し自身の文面かもしれない。
- **H2 設問の形**: `auto-explicit-multifile` は「User 作成後に何が起きるか」で、
  **物語的な締め**を誘う。実際、観測された 1 件の締めも 1 文の要約だった。
- **H3 メッセージ分割**: 言い直しと締めが**同じ 1 通**なら再発にならない。
  別々の assistant メッセージに分かれたときだけ最終結果が短くなる。
  分かれるかどうかはモデル次第で、直接は操作できない。

H1 は**製品の文面の問題**でもある。装置で頻度が上がるなら、
文面を「最後の 1 通に入れろ」に変える改修が別に要る（§7）。

## 3. 装置の構成（4 つのレバー）

| # | レバー | 根拠 | 実装 |
|---|---|---|---|
| L1 | リマインダ抜き | この構成の短縮率は 16/18 = 0.89（実測）。**block がほぼ毎 run 出る** | `check-worker-launch` の matcher を外した実験用コミット |
| L2 | `SENDBACK=on` | 2 段目を起こす前提 | 実行時の環境変数 |
| L3 | 締めを誘う設問 | H2 | 装置専用ケース（下記）。**実験用ブランチの `cases.json` にだけ置く。main には入れない**（課金スイートを太らせない） |
| L4 | 行数を増やす | 写す行が多いほど要約に流れやすい（仮説。観測 1 件は 5 行） | 装置ケースの fixture を 4〜5 ファイルにする |

装置専用ケース `relapse-narrative`（suite B、mode は `haiku` のみ）:

- `prompt_delegate` は既存の `auto-explicit-multifile` と同じ「何が起きるか」型で、
  **末尾に「最後に流れを 1 段落でまとめてください」を足す。**
- これは**再発の形を人工的に作っている**。§5 の解釈でそう明記する。
  「自然発生率を測る装置」ではなく「修正が効くかを見る装置」である。

## 4. 段階（安い順に、止められるように）

- **段階 0（課金なし）**: 判定器を書く。`evals/compare/relapse_probe.py`（新規）:
  CLI セッションから「締めの 1 通」と「それ以前の assistant テキスト」を分け、
  `sendback_retention.check_relapse` を当てて再発かどうかを返す。
  **フックが無い腕でも再発を数えられる**ことが要件（修正 off の腕はフックが
  block しないので、試行ログでは数えられない）。単体テストつき。
  実験中は変更しない。
- **段階 1（装置の検証、6 run、約 $1.1）**: 修正 **off** の構成（`3517831` の
  1 つ前）で装置を 6 run 回し、**再発が 3/6 以上**出るかを見る。
  - **3/6 未満なら装置は失敗。** そこで止める。修正は「オフライン検証のみ」と
    記録して閉じる。L3/L4 を足して測り直すのは**別の事前登録**とする。
- **段階 2（修正の A/B、1 腕 9 run、約 $3.2）**: 段階 1 が通ったときだけ。
  - treatment = 現 HEAD（修正入り）、control = `3517831` の 1 つ前。
  - 差は relapse 検査 1 点のみ。腕は交互。

**合計上限 $6。**

## 5. 事前登録する項目（段階 2）

| # | 項目 | 定義 |
|---|---|---|
| E1 | 再発の発生 | `relapse_probe` が再発と判定した run 数（両腕。装置が効いているかの確認） |
| E2 | 最終結果の保持（主要） | 再発した run のうち、**最終結果に行が残っている** run 数。control では定義上 0 に近いはず |
| E3 | relapse block | 試行ログで `outcome=blocked` かつ `relapse=true` の件数（treatment のみ） |
| E4 | 予算の遵守 | 1 セッションあたりの relapse block が**1 を超えない**こと。**期待値どおりなら 0 件超過** |
| E5 | 誤 block | S1（block したのに自分の checks が violation でない）。**期待値 0** |
| E6 | 費用 | run ごとの最終 `total_cost_usd` の和 |

判定基準（事前）:

1. **主要は E2 を分母つきで報告する。** 再発 run の分母が両腕合計 8 未満なら、
   率は出さず「装置が足りなかった」と記録する。
2. **E4 が 1 件でも超過したら、それは製品の後退である。** 修復率がいくら高くても
   「入れてよい」とは書かない。ループ防止が予算の唯一の根拠だからである。
3. **E5 ≥ 1 も同じ扱い。**
4. 中間解析はしない（費用の停止規則を除く）。段階 1 → 段階 2 の移行判定だけが
   事前に許された「途中で見る」点である。

## 6. この装置で言えないこと（先に書く）

- **自然発生率は測れない。** L3 で締めを誘っている以上、
  ここで出る再発率は製品の実利用の再発率ではない。
  30 run に 1 件という観測（`sendback-rescue` §3）のほうが自然発生に近い。
- **H3（メッセージ分割）は操作していない。** 装置が失敗するとしたら
  ここが理由である可能性が高い。失敗したらそう記録する。
- 段階 2 で E2 が両腕とも高ければ、「修正が効いた」ではなく
  「この装置では control でも行が残る」＝装置が再発を作れていない、と読む。

## 7. 装置が成功したら別に出てくる宿題（本記録では手を付けない）

H1 が当たっていた場合、`block_reason` の
「**before you finish**」は再発を誘う文面である。
**「最後の 1 通に入れろ」に変えるべき**かもしれない。
これは製品文面の変更であり、S1（誤 block）や修復率に影響しうるので、
**別の事前登録と別の測定**にする。今回の装置はその測定にもそのまま使える。
