# 送り戻しで短縮が救えるかの測定・事前登録（2026-09-16）

`reviews/launch-reminder-power-2026-09-16.md` §5 が残した問い。
**本記録は走らせる前にコミットする。** 腕・枠・N・項目・判定基準・停止規則を
先に固定する。**今回は中間解析を一切しない**（前回、事前登録が許していない
中間集計をした。その逸脱を繰り返さない）。

## 1. 問い

リマインダ（`check-worker-launch`）を入れても、親のパス短縮は 2/18 残った。
**送り戻し（`SENDBACK=on`）を入れると、その残りは救えるか。**

## 2. 率の比較では答えられない（事前に明記する）

残存率 2/18 = 0.111 を 0 に下げる効果を率で検出するのは、この予算では無理である。
完全に救えたとしても **2/18 対 0/18 の Fisher 両側 p = 0.49**。
1 腕 60 run 規模（$20 超）でようやく届く。

したがって主要評価項目は率ではなく、
**「block が出たとき直ったか」という条件つきの量**にする。
これは `reviews/sendback-fixed-n-probe-design-2026-09-16.md` §2 が採った立場と
同じで、フックが影響できるのは block を出した run だけだからである。

## 3. 腕と枠

枠はどちらも `auto-explicit-multifile/haiku`（短縮が出る枠）。`SENDBACK=on`。

- **腕 A（残存を直接見る）**: 現 HEAD（リマインダ入り）**18 run**。
  `SENDBACK=off` の実測 2/18（`launch-reminder-power`）と同条件・同 N で、
  違いは送り戻しだけ。
- **腕 B（条件つき修復率に検出力を与える）**: リマインダ抜き（HEAD から
  `check-worker-launch` の matcher だけを外した実験専用コミット）**12 run**。
  この構成の短縮率は 16/18 = 0.89 と実測済みなので、**block が 10 件前後出る**。
  P1 の分母を稼ぐのはこちらである。

腕 B は「リマインダ無しの世界」を測るためではない。**同じ失敗（親が
`confirmed:` 行を落とす）を高頻度で作り、送り戻しがそれを直せるかを見る装置**である。
腕 A の 2 件前後だけでは、直っても直らなくても何も言えない。

## 4. 事前登録する項目

計器は `evals/compare/sendback_probe.py`（`score_dir`、試行ログ
`*.jsonl.sendback.jsonl` + CLI セッション再判定）と
`evals/compare/retention_probe.py`（最終回答の短縮）。どちらも実験中に変更しない。

| # | 項目 | 定義 |
|---|---|---|
| R1 | 修復率（主要） | Stop で block した run のうち、最終回答の `line_retention` が ok になった割合（`sendback_probe` の P1）。腕 A・B 別に、分母つきで報告 |
| R2 | 子側修復 | SubagentStop で block した worker の修復数（P2） |
| R3 | 残存短縮（腕 A） | 最終回答が短縮していた run 数。`SENDBACK=off` の 2/18 と**記述的に**並べる |
| R4 | 誤 block | S1（block したのに自分の `checks` が violation でない）。**期待値 0** |
| R5 | 再 block 上限 | S4（`stop_hook_active` 下の再 block）。**期待値 0** |
| R6 | 未測定 | `p1_unmeasured` / `s3_unmeasured`。0 でないなら分母から外して明記する |
| R7 | 費用 | run ごとの最終 `total_cost_usd` の和（起動プローブ込み） |

## 5. 判定基準（事前）

1. **主要は R1 を分母つきで書く。** 母比率に一般化しない
   （固定 N プローブ §3 と同じ扱い）。
2. **R3 は記述のみ。** 2/18 対 x/18 で p を出しても意味が無いことは §2 で
   決めてある。結果が 0/18 でも「救えた」とは書かず、
   3 の法則の上限（0/18 なら ≤ 0.17）を添える。
3. **R4 ≥ 1 なら、それは製品の後退である。** 誤 block の中身を記録し、
   修復率がいくら高くても「入れてよい」とは書かない。
4. **腕 B の block が 6 件未満なら、R1 はその分母のまま報告する。**
   足さない（追加課金しない）。
5. **中間解析はしない。** 36 run 分が終わるか、上限に当たるまで集計しない。
   例外は R7（費用）だけで、これは停止規則のために毎 run 見る。

## 6. 費用

実測 $0.165/run（腕 A の枠）。送り戻しは再回答のターンを増やすので
**+25% を見込む**。腕 A 18 run ≈ $3.7、腕 B 12 run ≈ $2.3、**合計約 $6。上限 $8。**
累積が上限を超えたらその時点で止め、そこまでの N で §5 を当てる。

## 7. 実行条件

両腕とも専用ワークツリーに固定コミットで置き、生成物以外の差分なしを確認し、
そのチェックアウト内で `judge.py --selftest` を通してから走らせる。
腕は交互に回す。固定コミットと CLI 版を結果と一緒に報告する。
