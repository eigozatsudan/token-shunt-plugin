# フェンス送り返しが実機で効くかの検証・事前登録（2026-09-17）

`6d2c9c2` で入れた `child_no_body` の送り返しには**実機の裏付けが無い**。
オフラインのテスト 13 件は「フックがどう判定するか」を固定しただけで、
**worker が送り返しを受けて実際に言い直すか**は測っていない。

**走らせる前に本記録をコミットする。**

## 1. 検証する仮説

**`TOKEN_SHUNT_SENDBACK=on` のとき、worker の最終報告からコードフェンスが消える。**

根拠のある前提はここまで:

- `reviews/redmine-dose-2026-09-17.md` §5 で、`redmine-last-query` の auto 腕
  **12 run 中 3 run（25%）**が `child_no_body: code fence in child message` で落ちた。
- そのときの eval は **`SENDBACK=off`**（`evals/compare/run.sh:379`）。
  **つまり 25% は「文言だけで守られなかった率」である。**
- フックが実機で発火するか、発火して worker が直せるかは**未知**。

## 2. 設計

**同じ case・同じ問いを、`SENDBACK` だけ変えて走らせる。**

| 腕 | 設定 | 意味 |
|---|---|---|
| control | `SENDBACK=off` | §1 の 25% を出した設定そのもの |
| treatment | `SENDBACK=on` | 製品の既定値 |

- case は **`redmine-last-query` のみ**（違反が観測された唯一の case）。
- **`MODES=auto` で auto 腕だけ走らせる。** direct には worker が居らず、
  この問いに何も寄与しない。**寄与しない run に払わない。**
- **run ごとに交互に入れ替える**（off, on, off, on, ...）。
  時間順の交絡を構造的に消す（`scope-interleaved` と同じ理由）。

### 2.1 選択バイアスを先に認める

**この case は「違反が出たから」選んだ。** したがって control 腕の率は
**上振れした標本から選ばれた場所での再推定**であり、
**製品全体の違反率の推定ではない。** 平均への回帰で control が 25% を下回ることは
十分あり得る。§5 の打ち切り規定はそのために置く。

## 3. N と枠

**各腕 24 run、合計 48 run。結果を見て伸ばさない。**

観測された 25% が保たれるなら、**6/24 対 0/24 で Fisher 正確検定（両側）p = 0.0219。**
（16→0.101、20→0.047、24→**0.022**、28→0.010。24 を最小の実用点として選んだ。）

累計 **約 $64.8**、総枠 **$100**。**本段階の上限 $15**（見込み $10.6）。
1 run の見積りは**直近の最も高い実測**から: `redmine-last-query` の auto
transcript $0.1468 + probe 分 $0.069 ≒ **$0.22**。
送り返しは worker のターンを 1 つ増やすので**余裕を見て reserve $0.35**。

**run ごとに `spend.py --cap 15 --reserve 0.35` を通す**（`938ac4c`）。

## 4. 計器

### 4.1 主要な判定は judge が行う（フック自身ではない）

**製品を製品自身のパーサで合格させない。**
フェンスの有無は **`judge.py` の `has_code_fence`** が決める。
フックの `sendback_retention.check_code_fence` とは**別実装**であり、
judge は本測定で**変更しない**。

**「フェンス run」の定義（事前に固定）:**
その run の auto 腕の verdict が
`child_no_body: code fence in child message` で落ちていること。
`child_no_body` が**別の理由**（引用漏れ、fixture 本文不読）で落ちた run は
**フェンス run に数えない。**ただし**件数は記録する。**

### 4.2 フックが発火したかは別に読む

`SENDBACK=on` のとき runner は `SENDBACK_TRIAL_LOG` を
transcript の隣に置く（`run.sh:382-383`）。
そこから **`outcome == "blocked"` かつ `reason` にフェンスを含む記録**を数える。

**「フェンスが消えた」と「フックが消した」は別の主張である。**
treatment 腕でフェンスが 0 でも発火が 0 なら、**効いたのはフックではない。**

## 5. 解析（走らせる前に固定する）

**主要: フェンス run の割合、control 対 treatment、Fisher 正確検定（両側）。**
treatment が 0/24 なら**三の法則**で上限 3/24 = **12.5%** を併記する。

**副次、すべて事前に決めたもの:**

1. treatment 腕でフックが発火した run 数（§4.2）。
2. **`accuracy_any` を両腕で。** 言い直して事実を落とすなら、それは退行である。
3. **`child_status` と `child_msg_cap` を両腕で。**
   ターンが 1 つ増えて書式が壊れていないか。
4. **partial で終わった run 数**（`maxTurns` を使い切って言い直せなかった場合）。
5. auto の費用、両腕の**中央値を記述するのみ。検定はしない。**
   対になっていないので、ここで検定を足すのは後付けになる。

**中間解析はしない。**

## 6. 打ち切りと、事象が足りなかったときの書き方

- 費用が枠に達したとき（`spend.py` が止める）。
- 計器が定義どおり動いていないと分かったときに限り中止してよく、
  そのときは**何が定義と違ったかを数字で示す**。
- **結果の向きや大きさは、止める理由にならない。**

**control 腕のフェンス run が 4 未満だったとき:**
**「事象が足りず treatment を判定できなかった」と書く。**
§2.1 の選択バイアスが効いたということであり、
**フックが効いた証拠にも、効かなかった証拠にもならない。**
**N を足して測り直すかどうかは、そこで改めて決める。**

## 7. 予測を外したときにどう書くか（事前に決める）

- treatment でフェンスが**減らない**なら、「**送り返しは実機で効かなかった**」と書く。
  **`6d2c9c2` は入れたまま、効かなかったことを記録する**（害が無いことは §5-2,3 で見る）。
- **減ったが発火が 0 件**なら、「**減った理由はフックではない**」と書く。
- **フェンスは消えたが `accuracy_any` が落ちた**なら、
  **それは修正ではなく別の壊し方である**とはっきり書く。

## 8. 事前に認めている弱点

- **case は 1 つ、問いの形も 1 つ。** 他の case では違反が観測されていないので、
  **「製品全体で何割直るか」は本測定では分からない。**
- 選択バイアス（§2.1）。
- 費用は今日のモデル価格に依る。
- **treatment 腕は eval の baseline 設定ではない。**
  `SENDBACK=off` は baseline がスキルを測るための設定
  （`reviews/sendback-registration-decision-2026-09-15.md` §3.4）。
  本測定は**わざとそれを外している**ので、
  ここで得た数字を他の測定の baseline と並べてはならない。
