# Redmine での効果測定・事前登録（2026-09-17）

動作確認は `reviews/redmine-smoke-2026-09-17.md`（5 基準を満たした）。
**走らせる前に本記録をコミットする。**

**問い: 実コーパスで、token-shunt は親の文脈に入る量をどれだけ減らすか。**

## 1. 枠

新しい上限 **$100**（指定を受けた）。現在の累計 **$37.37**。
**本段階の上限は $25**（見込み $16）。総額の見込みは **$53.4**、最悪 $62.4。

**run ごとに `spend.py --cap` を通す。** 前回 $30 を $36.55 まで超えたのは、
書いた停止規則を実装しなかったからである（`reviews/scope-interleaved-2026-09-17.md` §6）。

見込みの立て方も変える: **直近の最も高い実測から取る。**
auto は $0.184/run（実測）。direct は親が 20.7k トークンを飲むので**その倍を見て** $0.4。
1 対（direct + auto）$0.6、20 対で **$12**。安全を見て枠は $25 とする。

## 2. 主要指標 —— なぜ `parent_added_utf8_bytes` か

動作確認 §4.1 で `parent_input_tokens` が 3 つの数（`uncached` /
`cache_read` / `cache_creation`）であり、**大部分がシステムプロンプトの
`cache_read` でファイル本文ではない**ことを記録した。
**3 つを足すと、ターンをまたいだキャッシュ再読を何重にも数える。**

そこで主要指標は **`parent_added_utf8_bytes`**（judge.py:483、
親に見えたテキストの UTF-8 バイト数）とする。

- **キャッシュの按分に一切依存しない。**
- 「親が本文を見たか」という主張そのものの直接の量である。
- 既存の `isolation: delegate_lt_direct_and_fixture` が**既に使っており**、
  テスト済みの経路である。新しい計器を測定のために作らない。

## 3. 対にする（同一 run 内で direct と auto を走らせる）

`redmine-visible-scope` に `direct` 腕を足し、**1 run が 1 対を生む。**
同じ fixture・同じ時刻・同じ CLI で、差は「プラグインを読むか否か」だけ。

**腕を別々の worktree に分ける必要が無い。** これまでのスコープ測定が
交互実行で苦労した時間差交絡は、対にすれば構造的に消える。

## 4. N を今ここで固定する

**20 対（= 20 run）。結果を見て伸ばさない。**

指標は二値ではなく連続量で、動作確認の 2 run では auto の
`cache_creation` が 9,892 と 9,222（差 7%）と**ばらつきが小さい。**
20 対あれば符号検定だけでも 2^-20 まで届く。**足りなければ足りないと書く。**

## 5. 解析（走らせる前に固定する）

**主要: 対ごとの `parent_added_utf8_bytes`（direct − auto）。**

1. **符号検定（両側、正確）**: auto < direct の対の数。
   分布の仮定を置かない。20/20 なら p = 1.9e-06。
2. **効果量**: (direct − auto) の**中央値・最小・最大**。
   **p ではなくこちらが答えである。**「いくら減るか」を問うている。
3. Wilcoxon 符号順位（両側、n ≤ 20 の正確分布を自前で計算）。scipy は使わない。

**副次、すべて事前に決めたもの:**

1. `parent_input_tokens` を **3 成分そのまま**両腕で報告する。**合計しない。**
2. run あたり実費を腕ごとに。**auto が高い可能性がある**（ワーカー呼び出しが増える）。
   **高ければ高いと書く。**
3. **両腕の正答（`gold_any`）。** direct は全文を持つので**より良く答えうる。**
   バイト数だけの比較は片面的であり、ここを併記しないと誤導になる。
4. `isolation` 判定（delegate < direct かつ delegate < fixture）の run ごとの合否。
5. verdict。**今回は腕の比較に使ってよい**（腕ごとに別の expect で判定され、
   スコープ測定のときのような「試みた時点で落ちる」非対称が無い）。

**中間解析はしない。止めるのは費用だけ。**

## 6. 事前に認めている弱点

- **1 case・2 ファイル・1 問いしか測っていない。** 一般化しない。
- **direct のほうが答えが良い可能性がある。** §5 副次 3 で必ず併記する。
  「バイトは減ったが答えも悪くなった」なら、**そう書く。**
- `parent_added_utf8_bytes` は親に見えたテキスト量であって、
  **課金トークンそのものではない。** 費用は副次 2 で別に見る。
