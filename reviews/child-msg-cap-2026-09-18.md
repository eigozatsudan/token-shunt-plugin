## 1. 漏れではない

超過した返答に**ファイル本文は入っていない**。
`child_no_body` は該当 run すべてで通っている
（落ちているのは `child_msg_cap` だけである）。

中身は**シンボルごとの構造化された要約**である。最長のもの（10,642 字）は
92 行で、コードブロックもフェンスも 0、各行が
`confirmed: Command.show_list() — defined at <絶対パス>:80 — …` の形をしている。

**correctness も落ちていない。** multiturn の超過 5 件は
**accuracy が 5/5 で 1、親の読み取りバイトは 5 件とも 0** である。
**長すぎるだけで、正しく、委譲もしている。**

## 2. 原因 — 課題の要求と製品の上限が衝突している

turn 1 の prompt はこう書いてある（A・B・multiturn で同一）。

> **各段の関数/メソッド名と、それが定義されている file の絶対パスを挙げよ。**

つまり課題が要求しているのは
**(a) 段数の決まっていない列挙**と **(b) 1 件ごとの絶対パス**である。
plugin 側の契約は **worker の返答 4,000 字**。

### 2.1 パスの反復は原因ではない。寄与に過ぎない

fixture の絶対 root は 68 字あり、返答ごとに 1〜43 回現れる。
返答に占める割合は**中央値 17%**（最大 30%）。

**しかし root を全部取り除いても、超過した 5 件は 1 件も上限内に入らない。**

| run | 字数 | root 反復ぶん | 除いた残り | 上限内に入るか |
|---|---|---|---|---|
| UWDv1roq | 10,642 | 2,924 (27%) | 7,718 | **入らない** |
| sM7k6XGD | 6,378 | 476 (7%) | 5,902 | **入らない** |
| evObSvPG | 5,770 | 680 (12%) | 5,090 | **入らない** |
| hiusl6C9 | 5,660 | 952 (17%) | 4,708 | **入らない** |
| p917Mmnp | 5,537 | 1,088 (20%) | 4,449 | **入らない** |

**「パスを相対にすれば直る」という最初の見立ては、この表で否定される。**
残るのは**列挙の長さ**である。最長の 1 件は 92 行あり、
**課題が「各段」と言った以上、段を全部挙げれば 4,000 字に収まらない。**

## 3. これが製品にとって何を意味するか

**上限が守られていないぶん、親は契約の最大 2.7 倍を受け取っている。**
それでも節約は残る —— multiturn で親に入ったコーパスは
direct 57,999 B に対し auto 1,110 B であり、
worker が親に渡した文字数は**会話あたり中央値 4,328 字**である。

**だから「効果が消える」という話ではない。**
**「4,000 字という約束が、3.5 回に 1 回守られていない」という話である。**

## 4. 決まっていないこと

1. **4,000 という数字が正しいかどうかを、本記録は何も言わない。**
   契約が破れていることだけを数えた。
2. **plan-phase（6.2%）と閾値下 3 本（28.6%）の差**は CI が重ならないが、
   **fixture も prompt も違う**ので、原因は特定できていない。
   ファイルが大きい regime のほうが**低い**という向きは、
   「大きいほど列挙が長くなる」という素朴な予想と逆である。**説明できない。**
3. **短く返していたら同じ精度だったか**は測っていない。
   超過 5 件は accuracy 5/5 だが、**上限内に収めた場合の対照が無い。**
