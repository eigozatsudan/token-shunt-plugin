## 2. なぜ起きなかったか（H1 は逆だった）

1 run のメッセージ列を見ると、順序が仮説と逆である。

```
msg 0  「大きい user.rb はワーカーに投げます」
msg 1  「ワーカーの戻りを待っています」
msg 2  ← 物語的なまとめ（## Flow after a User is created …）。ここで行を落とし、block
msg 3  ← 言い直し。confirmed: 行だけ。これが最終メッセージ
```

**設問で誘った「1 段落のまとめ」は block の前（msg 2）に出ており、
block 後の言い直し（msg 3）が turn の最後になっている。**
5 件の block すべてがこの形だった。

設計 §2 の H1 は「`block_reason` の *before you finish* が
『言い直してから締めろ』と読めるので再発を誘う」だったが、
**観測は逆で、言い直しが最後に来ている。** 少なくともこの枠では、
H1 は再発の原因ではない。§7 に置いた「文面を変えるべきかもしれない」という
宿題も、この証拠の上では**急がない**。

残るのは H3（メッセージ分割）である。`sendback-rescue` §3 の 1 件は
言い直しのあとにもう 1 通が出ていた。それが何に起因するのかは、
この装置では作れなかった。

## 3. 事前登録からの逸脱（記録）

**L4 を変えた。** 設計は「fixture を 4〜5 ファイルにして写す行を増やす」と
書いていたが、実装では**fixture は 3 本のまま**にし、設問に
「支えられる手順をファイル付きで列挙せよ」を足す形で行数を稼いだ。

理由: reader 契約は 1 起動あたり 3 パス上限なので、fixture を 4 本にすると
**2 起動になり、スコープ拒否（`8f25a98`）という別の失敗経路が混ざる**。
装置の目的は再発 1 点を作ることなので、混ぜないほうを採った。
走らせる前に決めた変更だが、事前登録の文面とは違うので逸脱として記録する。

## 4. これで言えること / 言えないこと

- **言えること**: この装置では再発を作れなかった（0/6、3 の法則で 95% 上限 0.39）。
  送り戻し自体はこの枠でも効いており、block 5 件すべてで修復、
  最終結果の保持は 6/6 だった。
- **言えないこと**: 「再発は起きない」とは言えない。
  `sendback-rescue` で 30 run に 1 件観測している。
  **頻度が低いという既知の事実が、別の装置で再確認されただけ**である。
- したがって `3517831` の実機確認は**未了のまま**である。
  オフラインでは 14 件のテストで固定してある。

## 5. 次にやるなら（今はやらない）

H3 を直接狙うしかない。案としては、block 後に**もう一度発話させる理由**を
作ること —— たとえば block 文面に追加の指示を含めない構成で、
turn の終わりに確認質問が出やすい設問を使う、など。
ただしこれは「再発を作るためにモデルの発話数を操作する」ことであり、
装置がさらに人工的になる。**費用と人工性の両方が上がるので、
別の事前登録として費用対効果を判断してからにする。**

ブランチ `exp/relapse-device`（`330d487`）は実験専用。main には入れない。
