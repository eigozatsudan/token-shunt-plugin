2. **direct 腕は観測できない**（§8.8）。`run.sh` は direct にだけ `--plugin-dir` を渡さないので、
   フックが 1 度も走らない。**「direct の被覆率が 0」は成果ではなく計器の不在である。**

   親の context 汚染は被覆率 0 でも起こりうる。**「coverage が低い = 親がきれい」ではない。**

## 6. 予算の逸脱（記録）

見積りはアーカイブの auto 1 会話あたり平均 $0.3724・最大 $0.5014 から取ったが、
**multiturn の実測は $1.4045 で 3.8 倍外れた。** 単発の 2 本は $0.14 と $0.19 で、
**外れたのは複数ターンのケースだけ**である。次に複数ターンを買うときはこの実測から取る。

また、3 本を別々の `--cap` で出そうとして 2・3 本目が走らずに止まった。
`drive.sh` は毎回**同じ run ディレクトリ**を `spend.py` に見せるので、
**cap は呼び出しごとではなく累積である。** 1 セントも無駄にしていない（走る前に止まった）。
再開時は cap を「その時点の実支出 + 1 本分」として `spend.py` から動的に取った。

## 7. `bytes` 列と `parent_bytes.py` の突き合わせ（2026-09-20、$0）

spec §6 は「`bytes` は `parent_bytes.py` と照合するために在る」と書いたまま、
1 度も照合していなかった。今日の 3 本の transcript で実施した。

| run | 被覆率計器の親 bytes | `parent_bytes.py` | 差 | 親の読み取り行数 |
|---|---|---|---|---|
| run.8bpx1reV | 1,209 | 1,329 | +120 | 30 |
| run.LWkKswLK | 63 | 83 | +20 | 5 |
| run.Duox7sd0 | 0 | 0 | 0 | 0 |

**差はどちらも 4 B/行ちょうどで、原因は行番号の接頭辞である。**
transcript の `tool_result` は `288\tdef render_header():` の形を持ち、
フックが見る `tool_response.file.content` は**素のファイル本文**である。
接頭辞を差し引くと **2 つの計器は完全に一致する。**

**どちらが「親に入ったバイト数」か。** 親の context に実際に入ったのは
**番号つきの方**である。したがって:

- **被覆率 CSV の `bytes` は、親の汚染を行あたり (行番号の桁数 + 1) B だけ過小に言う。**
  30 行の読み取りで 1,209 に対し 120 B、約 10% である。桁数が増えるほど広がる。
- **`bytes` を親の context 汚染の指標として単独で使わない。** その用途には
  `parent_bytes.py` がある。被覆率計器の `bytes` は**行の集合に値段を付けるための内部量**である。

敵対レビューが「両者は親の定義が違う（`agent_id`/`agent_type` 対 `parent_tool_use_id`）ので
食い違いうる」と指摘していた点については、**この 3 本では定義の差による食い違いは出ていない**
——親の読み取りがすべて本当に親のものだったためで、**worker が居る会話で再確認する必要は残る。**
