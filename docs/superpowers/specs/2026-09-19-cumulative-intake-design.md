# 会話累積の取り込みを機械強制する（Lock B、v0.2 範囲、2026-09-19）

対象の穴: `docs/2026-09-12-token-shunt-design.md` §26.2 の多ターン形。
実測: `reviews/multiturn-context-2026-09-18.md` §4-2（二重に訂正が入っている）。
関連: `reviews/cap-overflow-2026-09-19.md`（契約文 1 規則では直らなかった記録）。

**本書は設計のみである。実装も実機検証も本ブロックでは行わない。**
費用で成果を語らない（設計 652 行「費用は出荷可否の条件にしない」、
786 行「費用削減は未証明と表示する」）。

## 1. 対象と非対象

**v0.2 の範囲項目であり、v0.1 の出荷条件を動かさない。** §26.2 の
「総 I/O 超過の機械強制は v0.1 の範囲外」はそのまま残し、その下に
本書を v0.2 の手段として接続する。

`evals/compare/parent_turn_reads.py` は **観測必須・出荷ゲートにしない。**
§26.5 の「必須親トークン測定」と同じ扱いとする —— **欠測は fail、
件数 >0 それ自体は出荷を止めない。** 現在の実測（10/14 会話）で
ゲートにすれば v0.1 は出荷不可になるが、残高では合格の実証もできない。
**穴は README と §15 に数字で載せ、出荷は止めない。**

**この「必須」の範囲を取り違えない。** 多ターンケースを**走らせたとき**、
その記録を残すことが必須であり、欠測を fail とする。
**多ターンケース自体を §26.5 の必須スイートには加えない。**
加えれば、リリースのたびに 5 ターン会話の実行が要るようになり、
**出荷ゲートにしないと決めたものが課金を伴う出荷条件として裏口から入る。**
v0.1 の必須スイート（A 全件 + B 各モード 1 反復）は本書で変更しない。

### 数えるもの

親自身が発行し、**エラーなく返ってきた**読み取りが親のトランスクリプトへ
載せた UTF-8 バイト数を、セッション単位で累積する。対象ツールは `Read` と、
`check-bash-read` が既知 reader と認めている `Bash` 読み取りの両方。
Read だけを数えると `cat` 経由で台帳を迂回でき、§10 が既に持っている
deny 経路を使わない理由がない。

`is_error` の扱いは `parent_turn_reads.py` と揃える ——
**拒否された読み取りは 0 バイトである。** §4-2 の訂正の訂正
（拒否された Read を突破として数えた）を生んだ規則なので、
計器と強制機構で一致させる。

### 数えないもの

- worker 自身の読み取り（`agent_type` で除外。Lock A と同じ判定）
- 画像 / PDF / `.ipynb`（§9 のサイズゲート除外と揃える）
- `Grep` の content（§15 の既知の限界のまま。ここを拡げると封鎖範囲の
  拡大になり、§26.5「フックによる封鎖範囲は広げない」に触れる）
- プラグイン自身の状態ファイル

### やらないこと

費用の主張はしない。本書は「効く」と書かない。cap-overflow が示したのは
**規則は届いても決定点で使われないことがある**（§6.4）であり、Lock B は
その反例ではなく、**契約文ではなく deny に変える**という別の手段である。
効いたかどうかは §5 の測定を経て初めて言える。

## 2. 台帳の形と状態

**Lock A の機構を借りる。** `delegated_paths.state_file` は、セッション ID の
sha256 を名前にした JSON を `TMPDIR/token-shunt-delegated-<uid>/` に置き、
ディレクトリの所有者・パーミッション・symlink を毎回検査し、`O_NOFOLLOW` で
開いて書く。Lock B は**同じ関数群を再利用し、別の名前空間**
（`token-shunt-intake-<uid>/`）を使う。

```json
{"bytes": 12773, "turns": 3}
```

`turns` は強制に使わない。`parent_turn_reads.py` が事後に数えるものを
実行時にも残し、before/after の突き合わせに使う記録である。

**壊れた状態は空である。** Lock A の規則（`delegated_paths.py` docstring
16-20 行）を変えない —— 読めない・パースできない・セッション ID が無い・
書き込めない、のいずれでも**累積 0 として扱い、何も拒まない**。
fail-closed にすると tempfile 1 個でセッション中の全 Read が死ぬ。
**この機構は親の取り込みを抑えるためのもので、セッションを壊す権限を持たない。**

### 2 つのフックに分かれる

| 契機 | 役割 |
|---|---|
| `PostToolUse`（Read / 既知 reader の Bash） | 親の成功した読み取りが返した本文の UTF-8 バイト数を加算する。判定はしない |
| `PreToolUse`（同上） | **加算済みの累積が既に閾値超なら deny。** 今から読むものは測らない |

この順序により**閾値を跨いだ読み取り自体は通る**。PreToolUse は
`tool_response` を持たないので正確なバイト数を原理的に取れず、`st_size` で
近似すれば targeted Read を過大評価する。§26.2 の「判定のためにメタデータ
だけを使う」を守る限り精度は上がらない。**超過 1 回分を許す代わりに、
推定を 1 つも入れない。**

実測で掛かる唯一の会話（turn 2 で 10,619 B → turn 3 で 12,773 B、
累積 23,392 B）では turn 4 の 8,706 B を止める形になり、
**32,098 B が 23,392 B で頭打ちになる。**

**worker の読み取りは加算しない。** ここを誤ると、委譲が成功するほど
台帳が埋まり、**正しく動いた会話ほど早く deny される**逆向きの機構になる。

## 3. 閾値・リセット・逃げ道

### 3.1 閾値は 16,384 バイト

小仕事予算と同じ数字だが**適用範囲が違う** —— §26.2 の 16,384 は
ターンごとの判断単位、こちらは会話累積である。同じ数字を採る根拠は実測:

| 累積閾値 | auto で掛かる会話 | 掛かる turn |
|---|---|---|
| 16,384 B | **1/14** | turn 3 |
| 32,768 B | **0/14** | — |
| 65,536 B | 0/14 | — |

auto の会話累積は **13 本が ≤8,670 B、1 本だけ 32,098 B**。
32,768 では**動機になった当の 1 本（32,098 B）を取り逃がす。**
16,384 は**最悪の 1 本だけを止め、正常な 13 本に一度も掛からない。**
実測でその線を引ける閾値はこれだけである。

（出典 `reviews/data/multiturn-context-2026-09-18-turns.csv`。この CSV は
`parent_bytes.py` 由来で deny 本文 369 B を含む。累積 369 / 398 の会話は
ほぼ deny 本文である。32,098 の 1 本は成功 Read 由来で結論は変わらない。）

`TOKEN_SHUNT_SESSION_BUDGET_BYTES` で変更でき、**0 で完全に無効**
（既存の `TOKEN_SHUNT_MIN_LINES` 等と同じ扱い）。

**既定は 0（無効）である（2026-09-19 改訂、§7.4 に経緯）。**
16,384 は**測定でこの線を引ける唯一の値**であり、**出荷時の既定ではない。**
既定 16,384 で登録すると、必須スイート
`auto-routing-boundary-16k-minus` / `-equal`（`agent_zero: true`、
約 16 KB の fixture）で**正常な Read 1 回が累積を超えさせる**ため、
**未測定の機構が出荷可否を落とし得る**（§1「v0.1 の出荷条件を動かさない」）。
既定を 16,384 へ上げるのは **§5 を実行して初めて言える v0.2 の変更**である。

### 3.2 リセットしない

worker 起動でリセットする案は採らない。委譲 1 回で台帳が空になるなら
**些細な委譲を挟んでから読み放題**という迂回が成立し、機構が契約文に戻る。
ターン境界でもリセットしない —— **会話をまたいで累積しないことが穴の原因**
（§26.2 多ターン形）なので、そこを直さなければ何も直らない。

### 3.3 編集経路との緊張、とその解き方

単調な上限は長いセッションの後半で**編集経路を殺し得る**。
`auto-edit-grep-location` と `compare-edit-dense-lines` は
Grep → **原本の targeted Read** → Edit を path_ok の条件にしている（§26.5）。
累積が既に閾値超のセッションでこの targeted Read が deny されると、
**出荷ゲートに入っているケースが機構自身によって落ちる。**

**加算は全部、deny は全文読みだけ。**

| 読み取りの形 | 台帳に加算 | 超過後に deny |
|---|---|---|
| `offset`/`limit` の無い Read（全文） | する | **する** |
| `offset`+`limit` 付き targeted Read | する | **しない** |
| 既知 reader の Bash | する | する |

根拠:

1. 編集契約が要求するのは targeted Read だけで、除外対象が契約と一致する。
2. targeted Read は `limit` が構造的に有界で、350 行超は `check-file-size`
   が既に止める。
3. 多ターンの穴を作った 3 ファイルは**全文読み**だった（239 / 316 / 211 行を
   丸ごと）。**除外しても、実測された穴は塞がったままである。**

**`offset`+`limit` を刻んで読み続ける迂回は残る。**
（当初ここに「逐次 `limit=350` による迂回」と書いたが、**実装より穴を
広く書いていた** —— 免除は `offset` と `limit` の**両方**が付いた Read だけで、
`limit` だけの Read は超過後 deny される。2026-09-19 に狭めた。）
これは §15 の既知の限界であり、
§26.5 は eval の path_ok 違反として検出する側に置いている。
**Lock B はこの穴を新しく開けない。既にある穴を、既にある場所に残す。**
塞ぎに行くと封鎖範囲の拡大になり §26.5 に触れる。

### 3.4 偽陽性の代償

誤って deny されても親は委譲できる —— **製品が本来通したい経路そのもの**である。
**最悪でも「小さいものを委譲させられた」で済み、「作業が止まる」にはならない。**
台帳が壊れたとき何も拒まない（§2）のと合わせ、この機構の最大の害を
「余計な委譲 1 回」に閉じ込める。

## 4. deny 文言

拒む理由が既存 2 つと違う。`check-file-size` は「閾値を超えたファイル」を、
`delegated_paths` は「worker に渡したパス」を拒む。Lock B が拒むのは
**ファイルでもパスでもなく、このセッションで親が既に取り込んだ量**である。
3 つ目の理由なので 3 つ目として書く。既存 2 つの文面は変えない。

```
This session has already taken 23,392 bytes of file bodies into the
parent context (budget 16,384). Reading more here defeats the
delegation this plugin exists for. Hand this path to
/token-shunt:bulk-reader and use its report. The budget does not
reset; delegating is the way forward, not a way to clear it.
```

### 入れたもの

- **実数と予算を両方出す。** `check-file-size` の `lines=%s/%s` と同じ形。
  どれだけ超えたかを親が知らないと次に何をすべきか決められない。
- **理由を 1 文。** cap-overflow §6.3 は、追加文が worker に届き
  **出力の書式まで変えた**ことを示した（Fisher p = 1.72e-12）。**文面は届く。**
  理由を欠いた文面は「フックの気まぐれ」として迂回を探させる。
- **リセットしないと明言する。** 無いと親は「委譲すれば枠が空く」と推測し、
  §3.2 で塞いだ迂回を文言で開けてしまう。

### 入れなかったもの

**targeted Read を逃げ道として案内しない。** `check-file-size` の文面は
"For edits, use a targeted Read of the original that passes the hook" と
明示するが、**あちらでは targeted Read も同じ 350 行 / 64KiB に縛られる。**
Lock B では §3.3 の通り targeted Read が deny 対象外なので、同じ案内は
**「`limit` を付ければ通る」と教えることになり、§15 の既知の限界を
文書化された穴から推奨経路へ格上げしてしまう。**
穴を残すことと、穴を案内することは違う。

**「小さいから大丈夫」を否定する句の列挙を入れない。**
`delegated_paths.DENY` は親の言い訳を名指しで潰しているが、Lock B で
拒まれる Read は**定義上すべて「個別には小さくて通るはずのもの」**なので、
列挙しても全部同じ 1 つの言い訳にしかならない。冒頭の実数がその役を果たす。

**この文言は機構の一部ではない。** deny は exit コードで成立しており、
文面が読まれなくても Read は通らない。cap-overflow で崩れたのは
「文面が行動を変える」という仮定であって、**Lock B はその仮定に乗っていない。**

## 5. 事前登録 —— 効いたかどうかをどう測るか

### 5.1 まず、正直に書かねばならないこと

**Lock B は設計上、会話の 93% で何もしない。** 実測 14 本のうち
16,384 B を超えたのは 1 本で、残り 13 本は ≤8,670 B ——
**v0.1 が既に 13/14 で正しく委譲しているからである。**
集計値はほぼ全部「効かなかった会話」で占められ、**平均も中央値も動かない。
動かないのが正しい。**

検出力として致命的である。**率 1/14 ≈ 0.071 の変化を n=14/腕で解像できない。**
**本ブロックは有意性を主張しない。**

### 5.2 主要指標

auto 会話の累積親 corpus バイトの**上側**を 2 つの数で見る。

1. **最大値**（control / treated 各 1 つ）
2. **direct の最小 25,901 B を超えた会話数**

多ターンで新しく出た性質は「auto の最大 32,098 B が direct の最小
25,901 B を上回った」ことで、**製品の主張が壊れたのはそこ 1 点**である
（§2 の重なり）。平均ではなく上側が争点なので上側を主要指標に置く。
**これは記述であり、検定ではない。**

### 5.3 副次

- **Lock B の発火回数**（`TOKEN_SHUNT_HOOK_LOG` / `hook_response`）
- **発火した会話で、発火後に親が追加で取り込んだ corpus バイト。**
  **0 でなければならず、モデルの協力を必要としない。**
  0 でなければ機構の欠陥であり、cap-overflow の
  「見えていて使われなかった」とは別の話になる。

  既知の 9,767 / 11,613 / 7,966 B、239 / 316 / 211 行で両方成立しており、
  **実行結果を見る必要がない。**

### 5.7 予算 —— 組めない

auto 会話 1 本の実費は平均 **$0.3724**（`reviews/multiturn-context-2026-09-18.md`
§3.1）。n=14/腕で **14 × 2 × 0.3724 ≈ $10.43**、calibration と reserve を
足して **枠 $12〜13 が要る。**

**上限 $200 に対し残り約 $9.7 では足りない。** §5.1 の通り n=14 でも率は
解像できないので、**枠を削って n を減らす案は採らない** ——
解像できない測定を安く買うことになる。**予算が戻るまで実行しない。**

### 5.8 外したときの書き方

- **発火 0 回** → 「機構が効かない」ではなく**「条件が起きなかった」**。
  1/14 の率なら n=14 で 0 回は普通に起こる。cap-overflow の
  `cap_reached` 0/39 と**混同しない**（あちらは条件が 14 回成立していた）。
- **発火したのに発火後の取り込みが 0 でない** → 機構の欠陥。
  修正まで v0.2 に入れない。
- **上側が動かない** → **「決まらない」と書く。**
  下がったとも下がっていないとも書かない。
- いずれの場合も**費用で成果を語らない。**

TDD（RED を先に見た）。`state_file` は §2 の通り `delegated_paths` のものを
名前空間だけ替えて再利用しており、所有者・パーミッション・`O_NOFOLLOW` の
検査は 1 か所のままである。**実機では 1 度も動かしていない**（§5 は未実行）。

### 逸脱 1 —— 台帳の `turns` を `reads` に替えた

§2 は `{"bytes": N, "turns": M}` と書いた。**フック入力にターン境界が無い。**
ターン数を実行時に持つには `UserPromptSubmit` フックを新しく登録するしかなく、
**強制に使わない記録のためにフック面を広げることになる**（§1 の非拡大方針）。
実装は `{"bytes": N, "reads": M, "pending": [...]}` とし、
`reads` は**課金された読み取りの件数**である。ターンごとの内訳は従来どおり
事後に `parent_turn_reads.py` が出す。**数えているものの名前を合わせただけで、
強制の挙動は §2 のままである。**

### 逸脱 2 —— Bash の「既知 reader」判定を再実装しなかった

§1 は Read と既知 reader の Bash の両方を数えると書いたが、**どこで
reader と判定するかは書いていない。** 判定は `check-bash-read`（1,500 行）に
あり、そのリスト自身が「ここに無い reader は穴であって許可ではない」と
書いている。**Python 側に 2 つ目の写しを作らない。**

`check-bash-read` が reader をファイル操作対象つきで認識した 1 点
（`check_files_full` の入口）から `check-intake-budget --bash` を呼ぶ。
そこで (i) 既に超過なら deny、(ii) そうでなければ `tool_use_id` を
`pending` に記録する。PostToolUse の `record-intake` は
**`pending` にある `tool_use_id` の Bash だけ**を stdout のバイト数で課金し、
マークは 1 回で消える。**マークされていない Bash は課金しない** ——
`npm test` の出力は台帳に載らない。python3 が無い・落ちた場合は
`return 0` で**従来どおりの判定に戻る**（fail-open、§2）。

### 7.3 既定をどうするか —— 初版は 16,384 のまま残した

初版はここに「§3.1 の通り既定 16,384 で実装した。登録した時点で v0.1 の
必須スイートも Lock B が有効な状態で走る。判断が要る項目として残す」と
書いた。**その判断は §7.4 で既定 0 に倒した。** 本節は経緯として残す。
`TOKEN_SHUNT_SESSION_BUDGET_BYTES` で切り替える点は変わらないが、
**その環境変数が実際には届いていなかった**ことも分かった（§7.5）。

### 7.4 既定を 0 に倒した（2026-09-19、$0、レビュー反映）

§7 初版は既定 16,384 のまま「判断が要る項目」として残した。**既定 0 に倒す。**
§3.1 と本節を同時に更新しており、**既定値を黙って反転させてはいない。**

1. **必須スイートに具体的な発火経路がある。**
   `auto-routing-boundary-16k-minus` / `-equal` は `agent_zero: true` で
   約 16 KB の fixture を親自身に読ませるケースである。行番号込みの payload で
   1 回の正常な Read が 16,384 を超えるので、同一セッションで全文 Read が
   もう 1 度出れば deny → 委譲 → `agent_zero` 違反。**確定で落ちるのではなく
   新しいフレーク経路**だが、**境界を検証するために作ったケースが、
   同じ数字を再利用した Lock B の境界上に載っている。**
2. **既定 ON の 2 通りがどちらも §1 に抵触する。** ゲートを ON のまま走らせれば
   未測定の機構が出荷可否を落とし得る。ランナー側で 0 をピンすれば、
   **ゲートが検証する設定と出荷 ZIP の既定がずれる。**
   既定 0 なら**ゲートも ZIP も Lock B 以前の v0.1 と同一挙動**である。
3. **害の天井が低いことは既定 ON の理由にならない。** §3.4 の「余計な委譲 1 回」は
   利用者側の話で、`agent_zero` ケースでは委譲そのものが違反である。

実装は `MEASURED_BUDGET_BYTES = 16384`（§5 が測る値）と
`BUDGET_BYTES = 0`（出荷既定）を分けて持つ。

### 7.5 control / treated を作る経路がなかった

§7 初版は「control 腕はこの環境変数で作る」と書いたが、**そのままでは届かない。**
`run.sh` の `_claude_call` は `compgen -e` で `TOKEN_SHUNT_*` を全て unset し、
2 つだけ再 export する。**`TOKEN_SHUNT_SESSION_BUDGET_BYTES` はフックに届いていない。**

`SENDBACK` と同じ形で 1 行足した:

```bash
export TOKEN_SHUNT_SESSION_BUDGET_BYTES=${SESSION_BUDGET_BYTES:-0}
```

**ベースラインでは 0 に固定される** —— 呼び出し側の export が
未測定の機構をベースライン実行の中で有効にすることはない。
treated 腕だけが `SESSION_BUDGET_BYTES=16384` を渡す。
テストは `evals/compare/test_runner.py` の 2 件（pin とパススルー）。

### 7.6 昇格時の宿題 —— expect 契約の判断が 1 つ残る

既定を 16,384 へ上げるとき、`auto-routing-boundary-16k-minus` / `-equal` で
**「Lock B の deny 後に委譲したこと」を `agent_zero` 違反とするか、
機構の正常動作とするか**を決める必要がある。**本書では決めない** ——
昇格は §5 の実行結果とセットであり、**先に契約だけ動かすと、
測定前にゲートの意味が変わる。**
